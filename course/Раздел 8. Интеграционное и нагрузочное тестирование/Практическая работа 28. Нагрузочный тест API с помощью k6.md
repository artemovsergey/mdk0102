# Практическая работа 28. Нагрузочный тест API с помощью k6

### **Тема**
Нагрузочное тестирование REST API. Создание мини-API и написание нагрузочного сценария на k6: виртуальные пользователи, проверки (checks) и пороги (thresholds).

### **Цель**
Сформировать практические навыки нагрузочного тестирования:
*   Создание тестируемого API (SUT — system under test) на минимальном API ASP.NET Core.
*   Установка и проверка работы инструмента k6.
*   Написание нагрузочного сценария: виртуальные пользователи, длительность, паузы.
*   Формулировка требований к производительности через пороги (thresholds).
*   Запуск теста, анализ отчёта и интерпретация метрик (RPS, процентили, доля ошибок).

### **Теоретическая часть**

**Нагрузочный тест** отличается от функционального тем, что проверяет не правильность ответов, а поведение системы под нагрузкой: сколько запросов в секунду она обрабатывает, как быстро отвечает и не начинает ли ошибаться.

**Основные понятия k6:**
*   **Виртуальный пользователь (VU)** — «пользователь», который выполняет сценарий. Виртуальные пользователи работают параллельно.
*   **Итерация** — одно полное выполнение функции `export default function ()`.
*   **`options`** — объект с настройками теста: число пользователей, длительность, пороги.
*   **`check()`** — мягкая проверка ответа (например, статус 200). Провал проверки не останавливает тест, но ухудшает статистику.
*   **`thresholds`** — жёсткие требования к метрикам. Если порог нарушен, k6 завершается с кодом **99** — это удобно для CI.
*   **`sleep()`** — пауза между итерациями, имитирующая «думающего» пользователя.

**Основные метрики отчёта k6:**

| Метрика | Что означает |
|---------|--------------|
| `http_reqs` | Количество отправленных запросов и запросов в секунду (RPS) |
| `http_req_duration` | Время отклика: avg, min, med, max, p(90), p(95) |
| `http_req_failed` | Доля запросов с ошибкой |
| `checks` | Доля успешных проверок |
| `iterations` | Количество выполненных итераций |
| `vus` | Фактическое число виртуальных пользователей |

**Порядок работы с нагрузочным тестом:** сначала **smoke-тест** (1–2 виртуальных пользователя, несколько секунд) — убедиться, что сценарий и система работают; затем **нагрузочный тест** с плановым числом пользователей. В этой работе мы сразу запускаем небольшой нагрузочный тест (10 VU, 30 секунд) на локальный API.

### **Ход работы**

1.  Создайте проект мини-API по своему варианту (см. раздел «Варианты заданий») — в примере это `LibraryApi`:

    ```powershell
    dotnet new web -n LibraryApi
    cd LibraryApi
    ```

2.  Добавьте класс сущности (`Book.cs`) и замените содержимое `Program.cs` согласно примеру (или своему варианту). Обратите внимание: API запускается по фиксированному адресу `http://localhost:5080`, чтобы сценарий k6 всегда знал, куда обращаться.

3.  Соберите и запустите API:

    ```powershell
    dotnet build
    dotnet run
    ```

    Терминал с запущенным API не закрывайте — тест будет обращаться к нему. Проверить доступность можно в другом терминале:

    ```powershell
    Invoke-RestMethod http://localhost:5080/api/books
    ```

4.  Установите k6 (если ещё не установлен) одним из способов:

    ```powershell
    # Способ 1: winget
    winget install k6 --source winget

    # Способ 2: Chocolatey (от имени администратора)
    choco install k6

    # Способ 3 (portable): скачать ZIP-архив k6-v2.2.0-windows-amd64.zip
    # со страницы https://github.com/grafana/k6/releases, распаковать,
    # добавить папку с k6.exe в PATH
    ```

    Убедитесь, что инструмент работает:

    ```powershell
    k6 version
    # k6.exe v2.2.0 (commit/00a9a1b7f5, go1.26.5, windows/amd64)
    ```

5.  В папке проекта создайте файл сценария `load-test.js` (см. практический пример).

6.  Запустите нагрузочный тест из папки, где лежит `load-test.js`:

    ```powershell
    k6 run --summary-export=summary.json load-test.js
    ```

    Дождитесь окончания теста (30 секунд) и изучите отчёт: блок `THRESHOLDS` (выполнены ли пороги) и блок `TOTAL RESULTS` (метрики).

7.  Создайте папку `images` в корне репозитория и добавьте в неё скриншот итогового отчёта k6 с успешно пройденными порогами.

8.  Создайте файл `README.md` и заполните его согласно требованиям.

### **Практический пример**

**Задание:** создать мини-API «Библиотека книг» с двумя endpoint'ами и написать нагрузочный тест: 10 виртуальных пользователей, 30 секунд, требования — p(95) времени отклика меньше 500 мс и не менее 95 % успешных проверок.

**1. Сущность (`LibraryApi/Book.cs`):**

```csharp
namespace LibraryApi;

public class Book
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string Title { get; set; } = string.Empty;
    public string Author { get; set; } = string.Empty;
    public string Isbn { get; set; } = string.Empty;
    public bool IsBorrowed { get; set; }
}
```

**2. Мини-API (`LibraryApi/Program.cs`):**

```csharp
using LibraryApi;

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

var books = new List<Book>
{
    new()
    {
        Title = "CLR via C#",
        Author = "Джеффри Рихтер",
        Isbn = "978-5-496-01202-5",
    },
    new()
    {
        Title = "Алгоритмы. Построение и анализ",
        Author = "Томас Кормен",
        Isbn = "978-5-8459-1868-7",
    },
};

app.MapGet("/api/books", () => Results.Ok(books));

app.MapPost(
    "/api/books",
    (Book book) =>
    {
        book.Id = Guid.NewGuid();
        books.Add(book);
        return Results.Created($"/api/books/{book.Id}", book);
    }
);

app.Run("http://localhost:5080");
```

**3. Нагрузочный сценарий (`load-test.js`):**

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

// Настройки теста: 10 виртуальных пользователей в течение 30 секунд
export const options = {
  vus: 10,
  duration: '30s',
  thresholds: {
    http_req_duration: ['p(95)<500'], // 95 % запросов быстрее 500 мс
    checks: ['rate>0.95'],            // успешны не менее 95 % проверок
  },
};

// Действия виртуального пользователя
export default function () {
  const response = http.get('http://localhost:5080/api/books');

  check(response, {
    'статус ответа 200': (r) => r.status === 200,
    'получен непустой список': (r) => Array.isArray(r.json()) && r.json().length > 0,
  });

  sleep(0.5); // пауза между итерациями
}
```

**4. Запуск.** В одном терминале — API:

```powershell
cd LibraryApi
dotnet run
```

В другом (из папки проекта) — нагрузочный тест:

```powershell
k6 run --summary-export=summary.json load-test.js
```

**Фрагмент отчёта k6 (результат прогона на локальном API):**

```
  █ THRESHOLDS

    checks
    ✓ 'rate>0.95' rate=100.00%

    http_req_duration
    ✓ 'p(95)<500' p(95)=1.9ms

  █ TOTAL RESULTS

    checks_total.......: 1200    39.904268/s
    checks_succeeded...: 100.00% 1200 out of 1200
    checks_failed......: 0.00%   0 out of 1200

    ✓ статус ответа 200
    ✓ получен непустой список

    HTTP
    http_req_duration..............: avg=344.18µs min=0s    med=0s       max=3.28ms   p(90)=1ms      p(95)=1.9ms
    http_req_failed................: 0.00%  0 out of 600
    http_reqs......................: 600    19.952134/s

    EXECUTION
    iterations.....................: 600    19.952134/s
    vus............................: 10     min=10       max=10
```

**Как читать этот отчёт:**
*   оба порога выполнены (отмечены ✓): p(95) = 1,9 мс при требовании менее 500 мс; успешность проверок 100 %;
*   за 30 секунд выполнено 600 итераций и 600 запросов (~19,95 запросов в секунду при 10 пользователях и паузе 0,5 с);
*   ошибок нет: `http_req_failed` = 0 %;
*   локальный API отвечает за доли миллисекунды — для учебного стенда это нормально; на реальном сервере значения будут заметно выше.

Так как все пороги выполнены, k6 завершился с кодом 0. Если бы p(95) превысил 500 мс, код завершения был бы 99, а в отчёте появилась бы отметка ✗.

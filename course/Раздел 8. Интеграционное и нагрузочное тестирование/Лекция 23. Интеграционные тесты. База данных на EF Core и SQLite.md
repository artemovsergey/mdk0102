### **Подробное рассмотрение каждого пункта плана**

#### **1. Пирамида тестирования и место интеграционных тестов**

**Подробное объяснение:**

Пирамида тестирования — это модель, которая показывает, каких тестов должно быть больше, а каких — меньше:

```
        /\
       /E2E\          Мало тестов: медленные, дорогие, хрупкие
      /------\
     /Интегр.\        Средний слой: проверяют связки компонентов
    /----------\
   /   Юнит-    \     Много тестов: быстрые, дешёвые, стабильные
  /--------------\
```

| Уровень | Что проверяет | Скорость | Достоверность | Количество |
|---------|---------------|----------|---------------|------------|
| Юнит-тесты | Отдельный класс/метод в изоляции (зависимости — моки) | Миллисекунды | Логика | Много |
| Интеграционные | Взаимодействие 2+ реальных компонентов (код + БД) | Десятки–сотни мс | Логика + связка | Средне |
| E2E (сквозные) | Всё приложение через UI или API | Секунды–минуты | Всё вместе | Мало |

**Почему нельзя обойтись только юнит-тестами?**

Представьте метод репозитория:

```csharp
public async Task<List<Book>> GetByAuthorAsync(string author) =>
    await _context.Books
        .Where(b => b.Author.Contains(author))
        .OrderBy(b => b.Title)
        .ToListAsync();
```

Юнит-тест с моком `DbSet` проверит лишь то, что метод «что-то вернул». А вот ошибку в LINQ-запросе, неправильную конфигурацию модели EF Core или ограничение базы данных (например, уникальный индекс по ISBN) поймает только интеграционный тест с настоящей базой.

---

#### **2. Что такое интеграционный тест**

**Подробное объяснение:**

**Интеграционный тест** — это тест, который проверяет взаимодействие двух или более **реальных** компонентов системы. В отличие от юнит-теста, здесь мы не заменяем зависимости моками, а подключаем их по-настоящему: базу данных, файловую систему, HTTP-сервис.

В контексте нашего курса типичная цепочка выглядит так:

```
xUnit-тест → LibraryService → LibraryDbContext (EF Core) → База данных SQLite
```

**Что дают интеграционные тесты:**

*   проверяют, что LINQ-запросы корректно превращаются в SQL;
*   проверяют конфигурацию EF Core: имена таблиц, длину строк, обязательность полей;
*   проверяют ограничения базы данных: `UNIQUE`, `NOT NULL`, внешние ключи;
*   проверяют работу с транзакциями и сохранением данных;
*   ловят ошибки, которые невозможно увидеть на моках.

**Что НЕ нужно проверять интеграционными тестами:**

*   чистую логику без внешних зависимостей — для неё есть юнит-тесты;
*   вёрстку и поведение UI — для этого есть UI-тесты (Раздел 6);
*   то, что уже проверено фреймворком (например, что `SaveChanges` сохраняет данные — это гарантия EF Core, а не вашего кода).

**Взгляд тестировщика:** юнит-тесты — это проверка «правильно ли мы написали», а интеграционные — «правильно ли это работает вместе».

---

#### **3. Варианты тестовой базы данных**

**Подробное объяснение:**

Главный вопрос интеграционного тестирования: какую базу использовать в тестах? Вариантов четыре, и у каждого есть компромисс.

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **EF Core InMemory** (провайдер `Microsoft.EntityFrameworkCore.InMemory`) | Очень быстро, ничего не нужно устанавливать | Это **не SQL**: не проверяет ограничения и запросы реальной СУБД |
| **SQLite in-memory** | Настоящий SQL, ничего не нужно устанавливать, быстро | Диалект SQL отличается от PostgreSQL/SQL Server |
| **Локальная СУБД** (PostgreSQL, MySQL, SQL Server) | Максимальная достоверность | Требует установки и настройки, сложнее изолировать данные |
| **TestContainers** | Настоящая СУБД автоматически поднимается в Docker | Требует установленного Docker |

**Провайдер InMemory устаревает как подход к тестированию БД.** Его главный недостаток — он не выполняет настоящие SQL-запросы и не знает про `UNIQUE`-индексы. Тест может пройти, а на реальной базе запрос упадёт. В современной практике EF Core для тестов без установки сервера рекомендуют именно SQLite.

**Решение для нашего курса — SQLite in-memory.** Он даёт настоящий SQL (с оговорками диалекта), работает без установки СУБД и быстро запускается.

#### **4. Обзор TestContainers и почему в нашем курсе их нет**

**Подробное объяснение:**

TestContainers — популярная библиотека для .NET, которая во время выполнения тестов автоматически поднимает настоящую СУБД (или другой сервис) в Docker-контейнере, а после прогона — останавливает и удаляет его.

Выглядит это примерно так (обзорный пример, **в нашем курсе не используется**):

```csharp
// Пакет Testcontainers.PostgreSql
var postgres = new PostgreSqlBuilder()
    .WithImage("postgres:16")
    .Build();

await postgres.StartAsync();

var connectionString = postgres.GetConnectionString();
```

**Плюсы:** самая достоверная среда (PostgreSQL как в продакшене), автоматическое управление жизненным циклом, изоляция между запусками.

**Почему не подходит нам:** для работы TestContainers требуется установленный и запущенный Docker. В компьютерных классах колледжа Docker нет, поэтому основную тему мы строим на SQLite, а TestContainers упоминаем обзорно — как инструмент, который вы встретите в реальных командах и в CI/CD.

#### **5. SQLite in-memory и EF Core**

**Подробное объяснение:**

Для работы понадобится NuGet-пакет **Microsoft.EntityFrameworkCore.Sqlite** (актуальная версия — 10.0.12):

```bash
dotnet add package Microsoft.EntityFrameworkCore.Sqlite --version 10.0.12
```

**Шаг 1. Модель данных и контекст.**

```csharp
public class Book
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string Title { get; set; } = string.Empty;
    public string Author { get; set; } = string.Empty;
    public string Isbn { get; set; } = string.Empty;
    public bool IsBorrowed { get; set; }
}

public class LibraryDbContext : DbContext
{
    public LibraryDbContext(DbContextOptions<LibraryDbContext> options)
        : base(options) { }

    public DbSet<Book> Books => Set<Book>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Book>(entity =>
        {
            entity.ToTable("books");
            entity.HasKey(b => b.Id);
            entity.Property(b => b.Title).HasMaxLength(200).IsRequired();
            entity.Property(b => b.Author).HasMaxLength(150).IsRequired();
            entity.Property(b => b.Isbn).HasMaxLength(20).IsRequired();
            entity.HasIndex(b => b.Isbn).IsUnique();
        });
    }
}
```

Обратите внимание на `HasIndex(b => b.Isbn).IsUnique()` — это ограничение мы и будем проверять интеграционным тестом.

**Шаг 2. Создание базы данных в памяти.**

Ключевая особенность SQLite in-memory: база данных существует, **пока открыто соединение**. Если соединение закрыть, база исчезнет. Поэтому соединение открывают вручную и держат открытым на протяжении всех тестов:

```csharp
using Microsoft.Data.Sqlite;
using Microsoft.EntityFrameworkCore;

var connection = new SqliteConnection("DataSource=:memory:");
connection.Open(); // База живёт, пока соединение открыто

var options = new DbContextOptionsBuilder<LibraryDbContext>()
    .UseSqlite(connection)
    .Options;

await using var context = new LibraryDbContext(options);
await context.Database.EnsureCreatedAsync(); // Создаём таблицы по модели
```

*   `DataSource=:memory:` — специальная строка подключения SQLite: база создаётся в оперативной памяти, никаких файлов на диске.
*   `Microsoft.Data.Sqlite.SqliteConnection` — ADO.NET-соединение, которое мы контролируем вручную.

**Шаг 3. Работа с базой.** Дальше всё как обычно: `context.Books.Add(...)`, `SaveChangesAsync()`, LINQ-запросы. Для EF Core это настоящая база.

#### **6. Создание схемы базы данных в тестах**

**Подробное объяснение:**

Чтобы запросы работали, у базы должна быть схема (таблицы, индексы). В тестах есть два способа её создать:

| Способ | Как работает | Когда использовать |
|--------|--------------|--------------------|
| `Database.EnsureCreated()` | Создаёт схему **по текущей модели** EF Core, без миграций | В тестах — самый простой и быстрый вариант |
| `Database.Migrate()` | Применяет миграции проекта | Если нужно проверять сами миграции или схема в тестах должна совпадать с продакшеном |

**Важно:** `EnsureCreated()` и миграции несовместимы — если в проекте есть миграции, `EnsureCreated()` бросит исключение. Для тестов это не проблема: учебный тестовый проект миграции не использует.

Пример создания схемы:

```csharp
await using var context = new LibraryDbContext(options);
await context.Database.EnsureCreatedAsync();
```

Метод вызывается **один раз** после открытия соединения. Все последующие контексты, использующие то же соединение, увидят готовую схему.

#### **7. Изоляция данных между тестами**

**Подробное объяснение:**

Тесты не должны зависеть от порядка выполнения и друг от друга. Если один тест добавил книгу, другой тест не должен её увидеть (или должен учитывать её существование). На практике используют три подхода.

**Подход А. Новое соединение и новая база на каждый тест** — самый простой и надёжный:

```csharp
public class LibraryServiceTests : IDisposable
{
    private readonly SqliteConnection _connection;
    private readonly LibraryDbContext _context;

    public LibraryServiceTests()
    {
        _connection = new SqliteConnection("DataSource=:memory:");
        _connection.Open();
        _context = CreateContext();
        _context.Database.EnsureCreated();
    }

    private LibraryDbContext CreateContext()
    {
        var options = new DbContextOptionsBuilder<LibraryDbContext>()
            .UseSqlite(_connection)
            .Options;
        return new LibraryDbContext(options);
    }

    public void Dispose()
    {
        _context.Dispose();
        _connection.Dispose();
    }

    [Fact]
    public async Task AddBookAsync_NewBook_SavesToDatabase()
    {
        var service = new LibraryService(_context);
        var book = new Book { Title = "CLR via C#", Author = "Джеффри Рихтер", Isbn = "978-5-496-01202-5" };

        await service.AddBookAsync(book);

        Assert.Equal(1, await _context.Books.CountAsync());
    }
}
```

**Подход Б. Одна база на класс, уникальные данные в каждом тесте** — быстрее, но требует аккуратности. Общая база создаётся в фикстуре класса (`IClassFixture<T>`), а тесты используют уникальные ISBN.

**Подход В. Транзакция с откатом** — каждый тест выполняется в транзакции, которая в конце откатывается. Быстро, но требует дополнительной настройки и не подходит, если код сам управляет транзакциями.

**Рекомендация для учебных проектов:** подход А — минимум магии, максимум надёжности. Именно его мы применим в практической работе.

#### **8. Когда писать юнит-тест, а когда интеграционный**

**Подробное объяснение:**

| Проверяем | Тип теста |
|-----------|-----------|
| Расчёт скидки, валидацию строки, ветвления `if/else` | Юнит-тест (быстрый, с моками) |
| Сохранение сущности в базу, чтение по условию | Интеграционный (SQLite in-memory) |
| Ограничение `UNIQUE` по ISBN | Интеграционный |
| Конфигурацию модели EF Core (длины, обязательность) | Интеграционный |
| Вызов внешнего метода-зависимости (что вызвался один раз) | Юнит-тест с Moq |

**Практическое правило:** логику покрываем юнит-тестами, а «швы» между кодом и внешним миром — интеграционными. В одном проекте они прекрасно сосуществуют: `dotnet test` запускает и те, и другие.

---

### **Резюме**

1.  **Интеграционный тест** проверяет взаимодействие реальных компонентов: в нашем случае — сервиса, EF Core и базы данных.
2.  **Пирамида тестирования**: юнит-тестов должно быть много, интеграционных — меньше, но без них нельзя проверить работу с базой.
3.  **SQLite in-memory** — реальная база данных, работающая в оперативной памяти. Не требует установки СУБД и поддерживает настоящий SQL с ограничениями (`UNIQUE`, `NOT NULL`).
4.  **Ключевая особенность**: соединение `SqliteConnection` должно быть открыто на протяжении всего времени работы с базой в памяти.
5.  **Схема в тестах** создаётся через `EnsureCreated()` — по текущей модели EF Core, без миграций.
6.  **Изоляция**: самый простой вариант — новое соединение и новая база на каждый тест (конструктор + `Dispose`).
7.  **TestContainers** — инструмент для тестирования с настоящей СУБД в Docker; в нашем курсе не используется, так как Docker в классах нет.

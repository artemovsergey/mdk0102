#### **1. Нагрузочное тестирование: цели и место среди других видов тестирования**

**Подробное объяснение:**

Все рассмотренные ранее виды тестирования (юнит-тесты, интеграционные, UI-тесты) проверяют **функциональность**: правильно ли система выполняет свои операции. **Нагрузочное тестирование** отвечает на другой вопрос: как поведёт себя система, когда её одновременно используют десятки, сотни или тысячи пользователей.

Цели нагрузочного тестирования:
*   определить пропускную способность — сколько запросов в секунду выдерживает система;
*   найти узкие места (медленный SQL-запрос, нехватка памяти, блокировки, лимиты сети);
*   убедиться, что при плановой нагрузке время отклика приемлемо для пользователей;
*   проверить поведение системы при пиковых нагрузках и её восстановление после перегрузки;
*   получить данные для планирования мощностей (сколько серверов и какой конфигурации нужно).

Нагрузочное тестирование относится к **нефункциональным** видам тестирования (проверка производительности). Его обычно выполняют на отдельном стенде, по конфигурации близком к продуктивному, чтобы результаты были достоверными.

---

#### **2. Ключевые метрики производительности**

**Подробное объяснение:**

*   **Пропускная способность (throughput), запросов в секунду (RPS)** — сколько запросов система обрабатывает за секунду.
*   **Время отклика (response time, latency)** — время от отправки запроса до получения ответа. Измеряется в миллисекундах.
*   **Процентили (p90, p95, p99)** — значение, ниже которого уложились 90 %, 95 % или 99 % запросов. Среднее значение обманчиво: единичные «медленные» запросы почти не влияют на среднее, но сильно портят опыт части пользователей. Именно процентили показывают «хвост» распределения. Пример: среднее время 120 мс, но p99 = 2 с — значит, каждый сотый пользователь ждёт 2 секунды.
*   **Доля ошибок (error rate)** — процент запросов, завершившихся ошибкой (HTTP 4xx/5xx, таймаут, обрыв соединения).
*   **Количество виртуальных пользователей (Virtual Users, VU)** — сколько «пользователей» одновременно работает с системой.
*   **Итерации (iterations)** — сколько раз виртуальные пользователи полностью выполнили сценарий.

Требования к производительности принято формулировать через процентили. Например: «при 50 одновременных пользователях 95 % запросов должны отвечать быстрее 500 мс, доля ошибок — менее 1 %».

#### **3. Виды нагрузочных тестов**

**Подробное объяснение:**

| Вид | Нагрузка | Цель |
|-----|----------|------|
| **Smoke (дымовой)** | 1–2 VU, 1–2 минуты | Убедиться, что скрипт корректен и система отвечает |
| **Load (нагрузочный)** | Плановая рабочая нагрузка | Устойчивость системы при обычной работе |
| **Stress (стрессовый)** | Постепенно выше плановой, до отказа | Найти предел возможностей и точку отказа |
| **Spike (пиковый)** | Резкий кратковременный скачок | Переживёт ли система всплеск (например, начала продаж) |
| **Soak (выносливость)** | Плановая нагрузка в течение нескольких часов | Выявить утечки памяти и постепенную деградацию |

Начинают всегда со smoke-теста: он быстро показывает, что сценарий написан верно, а система доступна. Только после этого переходят к нагрузочным и стрессовым испытаниям.

---

#### **4. Обзор инструментов нагрузочного тестирования**

**Подробное объяснение:**

| Инструмент | Язык сценариев | Особенности |
|------------|----------------|-------------|
| **Apache JMeter** | GUI + XML-планы | Ветеран рынка, много возможностей, но тяжёлый интерфейс и громоздкие планы |
| **Locust** | Python | Распределённый запуск, веб-интерфейс, код сценариев на Python |
| **NBomber** | C# (.NET) | Нагрузочные тесты на знакомом стеке .NET, интеграция с xUnit |
| **k6** | JavaScript | Лёгкий CLI, простые скрипты, встроенные метрики и пороги, удобен в CI |

В этом курсе используется **k6** (Grafana k6): он устанавливается одной командой, не требует графического интерфейса, а сценарии пишутся на JavaScript — языке, с которым студенты уже знакомы по фронтенду. Кроме того, k6 умеет проверять **пороги (thresholds)** и возвращать особый код завершения при их нарушении — это делает его удобным для CI-пайплайнов.

#### **5. Установка k6**

**Подробное объяснение:**

В Windows k6 устанавливается одним из способов:

```powershell
# Способ 1: через менеджер пакетов winget
winget install k6 --source winget

# Способ 2: через Chocolatey (требуются права администратора)
choco install k6

# Способ 3 (portable): скачать ZIP-архив со страницы
# https://github.com/grafana/k6/releases, распаковать и добавить папку в PATH
```

Проверка установки:

```powershell
k6 version
# k6 v2.2.0 (go1.24, windows/amd64)
```

Актуальная версия инструмента — **k6 v2.2.0**. Обновить k6 при portable-установке можно, скачав новый архив с той же страницы релизов.

#### **6. Первый сценарий: виртуальные пользователи и итерации**

**Подробное объяснение:**

Нагрузочный сценарий k6 — это обычный файл `load-test.js` с двумя обязательными элементами:

*   `export const options` — настройки теста (сколько пользователей, как долго);
*   `export default function ()` — функция, которую выполняет каждый виртуальный пользователь. Она вызывается в цикле: одна её полная выполнение — это одна **итерация**.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

// Настройки теста
export const options = {
  vus: 10,
  duration: '30s',
};

// Сценарий виртуального пользователя
export default function () {
  const response = http.get('https://jsonplaceholder.typicode.com/posts');

  // Проверка результата (в отчёте считается статистика по проверкам)
  check(response, {
    'статус ответа 200': (r) => r.status === 200,
  });

  // Пауза между итерациями — имитация «думающего» пользователя
  sleep(1);
}
```

Разбор примера:
*   `vus: 10` — десять виртуальных пользователей работают одновременно;
*   `duration: '30s'` — тест длится 30 секунд;
*   `http.get(...)` — отправка GET-запроса (модуль `k6/http`);
*   `check(...)` — мягкая проверка: её результат подсчитывается, но тест не прерывается;
*   `sleep(1)` — секундная пауза после каждой итерации, чтобы нагрузка была реалистичной.
*   Официальная площадка для тренировок k6 — публичный сервис `https://test-api.k6.io`; в примерах курса мы используем `jsonplaceholder.typicode.com`, как и в предыдущих практических работах.

#### **7. Настройка теста: options, stages, thresholds, checks**

**Подробное объяснение:**

**Простые настройки** (`vus` + `duration`) подходят для smoke- и простых нагрузочных тестов. Для имитации реального трафика используют **ступени (stages)** — постепенный разгон и спад нагрузки:

```javascript
export const options = {
  stages: [
    { duration: '30s', target: 20 }, // разгон до 20 виртуальных пользователей
    { duration: '1m', target: 20 },  // удержание нагрузки
    { duration: '20s', target: 0 },  // плавный спад
  ],
};
```

**Пороги (thresholds)** — это требования к метрикам, записанные формально. Если хотя бы один порог нарушен, k6 завершается с кодом **99** (это сигнал ошибки для CI):

```javascript
export const options = {
  vus: 10,
  duration: '30s',
  thresholds: {
    http_req_duration: ['p(95)<500'], // 95 % запросов быстрее 500 мс
    http_req_failed: ['rate<0.01'],   // доля ошибок меньше 1 %
    checks: ['rate>0.95'],            // успешны минимум 95 % проверок
  },
};
```

**Проверки (checks)** отвечают на вопрос «верен ли отдельный ответ»: статус 200, наличие нужного поля, корректный JSON. В отличие от порогов, проваленная проверка **не останавливает** тест — она лишь ухудшает статистику. А вот `thresholds` — это жёсткие критерии приёмки: их нарушение тест проваливает.

Дополнительные возможности (кратко):
*   `sleep` — пауза между итерациями;
*   `scenarios` и исполнители (executors) — сложные профили нагрузки (например, постоянно прибывающие пользователи);
*   `groups` — группировка запросов внутри сценария;
*   `--summary-export` — сохранение итогового отчёта в JSON.

#### **8. Запуск теста и чтение отчёта**

**Подробное объяснение:**

Запуск сценария выполняется командой `k6 run`:

```powershell
# Базовый запуск
k6 run load-test.js

# Сохранить итоговый отчёт в JSON (пригодится в CI)
k6 run --summary-export=summary.json load-test.js

# Переопределить количество пользователей и длительность без правки файла
k6 run --vus 20 --duration 1m load-test.js
```

Пример вывода k6 (сокращённо):

```
  scenarios: (100.00%) 1 scenario, 10 max VUs, 1m0s max duration

✓ статус ответа 200

     checks.........................: 100.00% ✓ 290      ✗ 0
     http_req_duration..............: avg=115ms min=95ms med=110ms max=430ms p(90)=150ms p(95)=180ms
       { expected_response:true }...: avg=115ms min=95ms med=110ms max=430ms p(90)=150ms p(95)=180ms
     http_req_failed................: 0.00%   ✓ 0        ✗ 290
     http_reqs......................: 290     9.6/s
     iterations.....................: 290
     vus............................: 10      min=10   max=10
```

Как читать отчёт:
*   **checks** — доля успешных проверок: 100 % (290 успешных, 0 проваленных);
*   **http_req_duration** — время отклика: среднее 115 мс, p(95) = 180 мс;
*   **http_req_failed** — доля ошибок 0 %;
*   **http_reqs** — всего 290 запросов, ~9,6 запросов в секунду;
*   **iterations** — столько раз пользователи выполнили полный сценарий;
*   **vus** — фактическое число виртуальных пользователей во время теста.

Если заданы пороги, в конце отчёта появится блок `THRESHOLDS` с отметками ✓/✗, а при нарушении порога команда завершится с кодом 99.

### **Резюме**

1.  Нагрузочное тестирование проверяет производительность системы под нагрузкой: пропускную способность, время отклика и стабильность.
2.  Ключевые метрики — RPS, время отклика с процентилями (p90/p95/p99), доля ошибок, число виртуальных пользователей.
3.  Основные виды тестов: smoke, load, stress, spike, soak — каждый отвечает на свой вопрос о поведении системы.
4.  k6 — современный инструмент нагрузочного тестирования: скрипты на JavaScript, установка одной командой, работа из командной строки.
5.  Сценарий k6 состоит из объекта `options` (настройки) и функции `default` (действия виртуального пользователя); `sleep` задаёт паузу между итерациями.
6.  `checks` — мягкие проверки ответов, `thresholds` — жёсткие критерии приёмки; нарушение порога даёт код завершения 99, что удобно для CI.
7.  Отчёт k6 содержит все ключевые метрики; `--summary-export` сохраняет результаты в JSON для дальнейшего анализа и артефактов CI.

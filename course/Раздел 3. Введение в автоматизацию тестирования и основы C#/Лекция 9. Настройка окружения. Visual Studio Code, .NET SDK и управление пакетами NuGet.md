### **Подробное рассмотрение каждого пункта плана**

#### **1. Экосистема .NET: Runtime, SDK и что из этого нужно тестировщику**

**Подробное объяснение:**

Любое приложение .NET, включая автотесты, работает в определённом окружении. Для нас важны три компонента:

*   **.NET Runtime (среда выполнения):** «двигатель», который выполняет скомпилированный код. Без него приложение или тест не запустится. Runtime есть на целевых машинах пользователей.
*   **.NET SDK (Software Development Kit):** набор инструментов для разработки: компиляторы, библиотеки, шаблоны проектов и — что для нас главное — **инструменты сборки и запуска тестов**. SDK — это мастерская, Runtime — двигатель.
*   **Редактор или IDE:** рабочее место, где мы пишем код, запускаем тесты и разбираем ошибки. В нашем курсе это **Visual Studio Code**.

| Компонент | Что умеет | Кому нужен |
|-----------|-----------|------------|
| .NET Runtime | Запускать готовые приложения и тесты | Пользователи, серверы |
| .NET SDK | Собирать, запускать, тестировать, управлять пакетами | Разработчики, тестировщики-автоматизаторы |
| Visual Studio Code | Редактировать код, запускать и отлаживать тесты | Разработчики, тестировщики |

**Почему это важно именно тестировщику:**

1.  **Понимание дефектов.** Ошибка «Could not load file or assembly» или «Тестовый хост не запустился» почти всегда связана с окружением: не установлен Runtime, нет нужной версии SDK, потерялся пакет. Зная компоненты, вы точнее опишете дефект и быстрее поймёте причину.
2.  **Запуск автотестов.** Все фреймворки тестирования (.NET, xUnit, NUnit, Selenium WebDriver) собираются и запускаются через .NET SDK.
3.  **Независимость.** Вы сами можете развернуть тестовый стенд и локально воспроизвести падение теста, не дожидаясь разработчиков.
4.  **Чтение логов.** В логах сборки и выполнения всегда указаны версии .NET и восстанавливаемые пакеты NuGet. Без этих знаний анализ логов затруднён.

> **Что такое LTS.** Microsoft выпускает новую версию .NET каждый год. Чётные версии (8, 10…) — **LTS** (Long-Term Support, долгосрочная поддержка, 3 года), нечётные (9, 11…) — STS (18 месяцев). Для учебных проектов и рабочих стендов выбирают LTS. Актуальная LTS-версия на момент изучения — **.NET 10** (поддержка до ноября 2028 года).

#### **2. Установка .NET SDK 10 (LTS) и проверка установки**

**Подробное объяснение:**

1.   Перейдите на официальный сайт: [https://dotnet.microsoft.com/download](https://dotnet.microsoft.com/download)
2.   Выберите версию **.NET 10** с пометкой **LTS**. Скачайте установщик для Windows (.exe) и запустите его: установка стандартная («Далее — Далее — Готово»).
3.   Если у вас установлен пакетный менеджер `winget`, можно установить SDK командой:
     ```powershell
     winget install Microsoft.DotNet.SDK.10
     ```

**Проверка установки.** Откройте терминал (VS Code или PowerShell) и выполните:

```bash
dotnet --version
```

В ответ вы должны увидеть версию, например:

```
10.0.300
```

Полезно проверить и полный список установленных SDK:

```bash
dotnet --list-sdks
```

Пример вывода, когда на машине несколько версий:

```
8.0.421 [C:\Program Files\dotnet\sdk]
10.0.300 [C:\Program Files\dotnet\sdk]
```

Это нормальная ситуация: один компьютер может содержать несколько SDK одновременно. При сборке конкретного проекта используется версия, подходящая его целевому фреймворку (target framework).

**Ключевые команды CLI:**

| Команда | Назначение |
|---------|-----------|
| `dotnet new <шаблон>` | Создать новый проект по шаблону |
| `dotnet build` | Скомпилировать проект |
| `dotnet run` | Скомпилировать и запустить приложение |
| `dotnet restore` | Восстановить пакеты NuGet по файлу проекта |
| `dotnet test` | Собрать и **запустить тесты** — ключевая команда тестировщика |

**Пример для тестировщика:** на сервере CI нет графического интерфейса и нет IDE — набор тестов запускается командой `dotnet test MyTests.csproj`. Поэтому команды CLI нужно уверенно знать до того, как вы нажмёте «зелёную стрелку» в редакторе: за любой кнопкой скрывается одна из этих команд.

#### **3. Visual Studio Code: редактор и инструменты для C# и тестов**

**Подробное объяснение:**

**Visual Studio Code (VS Code)** — бесплатный кроссплатформенный редактор Microsoft. Он легче «полной» Visual Studio, быстро работает на слабых машинах, а с расширениями даёт всё необходимое для C#-разработки и тестирования.

**Шаги по установке:**

1.   Скачайте VS Code с официального сайта: [https://code.visualstudio.com/](https://code.visualstudio.com/) и установите.
2.   Установите расширение **C# Dev Kit** (официальное расширение Microsoft для C#). Оно автоматически подтянет базовые расширения **C#** и **.NET Install Tool**.
3.   Проверьте работу: создайте или откройте проект на C# — редактор предложит подсказки, подсветку и навигацию по коду.

> **Замечание про Visual Studio.** Классическая Visual Studio 2022 не открывает проекты на .NET 10 — для них требуется Visual Studio 2026 (v18+). Поэтому в курсе мы работаем в **VS Code + .NET SDK 10**: эта связка бесплатна, актуальна и одинаково выглядит на любом компьютере.

**Ключевые элементы интерфейса для тестировщика:**

*   **Панель Explorer / Solution Explorer:** структура папки проекта или решения — файлы, зависимости, ссылки на проекты.
*   **Редактор кода:** основное пространство для написания кода и тестов.
*   **Встроенный терминал** (Ctrl + `): здесь выполняются команды `dotnet build`, `dotnet test`, `dotnet add package`.
*   **Панель Testing (иконка колбы):** VS Code находит тесты в проекте, позволяет запускать их по одному, группами или все сразу, показывает результат (зелёная галочка — тест пройден, красный крест — упал) и вывод теста.
*   **Палитра команд** (Ctrl + Shift + P): быстрый доступ ко всем командам расширений.

**Как открыть проект.** В VS Code принято открывать **папку с проектом** или решением: *File → Open Folder…* и выберите папку, где лежит файл `.sln` или `.csproj`. C# Dev Kit сам найдёт решение и покажет Solution Explorer — отдельно открывать `.sln` двойным щелчком не нужно.

**Практический пример:** откройте папку с проектом, затем панель Testing — через пару секунд VS Code соберёт проект и отобразит список тестов. Именно так вы будете работать с автотестами большую часть времени.

#### **4. Управление пакетами с помощью NuGet: файл проекта, CLI и редактор**

**Подробное объяснение:**

Ни один современный проект не пишется с нуля — мы используем сторонние библиотеки. Для .NET основным менеджером пакетов является **NuGet**.

*   **Пакет (Package):** архив с собранной библиотекой (DLL) и метаданными о зависимостях.
*   **Источник пакетов (репозиторий):** официальный каталог — [nuget.org](https://www.nuget.org/). Компании могут разворачивать и приватные репозитории.
*   **Версия:** у пакета есть семантическая версия (`4.49.0`). Для учёбы выбирайте **стабильные** версии: предварительные (preview, beta) могут содержать ошибки.

**Файл проекта `*.csproj` — конфигурация зависимостей.** При добавлении пакета в файл проекта появляется запись:

```xml
<ItemGroup>
  <PackageReference Include="Selenium.WebDriver" Version="4.49.0" />
</ItemGroup>
```

Этот файл хранится в Git, а сами пакеты — нет: любой участник команды (или сервер CI) восстановит их командой `dotnet restore`.

**Способы добавить пакет:**

**Способ 1: CLI .NET (основной в нашем курсе).** Самый универсальный и воспроизводимый способ, работает в терминале VS Code:

```bash
# Добавить пакет последней стабильной версии
dotnet add package Selenium.WebDriver

# Добавить конкретную версию (рекомендуется фиксировать)
dotnet add package Selenium.WebDriver --version 4.49.0
```

Проверить список зависимостей проекта можно командой:

```bash
dotnet list package
```

А удалить пакет — командой `dotnet remove package Selenium.WebDriver`.

**Способ 2: Solution Explorer в VS Code.** В обозревателе решений (C# Dev Kit) щёлкните правой кнопкой по узлу **Packages** и выберите добавление пакета — мастер предложит поиск и выбор версии.

**Способ 3: расширения редактора.** В Marketplace есть расширения для работы с NuGet (например, NuGet Gallery) — они добавляют поиск и установку пакетов прямо в интерфейсе.

Выбрать нужную версию удобно на странице пакета на [nuget.org](https://www.nuget.org/) во вкладке **Versions**.

**Пример для тестировщика:** чтобы написать первые UI-тесты, в проект нужно добавить пакет `Selenium.WebDriver` — мы сделаем это через `dotnet add package`, зафиксировав версию в `.csproj`. Через месяц на другой машине `dotnet restore` восстановит ту самую версию — поведение тестов не изменится «сами собой».

#### **5. Создание и запуск первого тестового проекта (`dotnet new xunit`)**

**Подробное объяснение:**

**Шаг 1. Создание проекта.** Выполните в терминале:

```bash
dotnet new xunit -n MyFirstTestProject
cd MyFirstTestProject
code .
```

Команда `dotnet new xunit` создаёт проект с уже подключённым фреймворком тестирования xUnit — тем, который мы будем изучать в следующих лекциях. Посмотреть все доступные шаблоны можно командой `dotnet new list`.

**Шаг 2. Анализ созданного проекта.** Структура:

```
MyFirstTestProject/
├── UnitTest1.cs              # первый тестовый класс
└── MyFirstTestProject.csproj # файл проекта с зависимостями
```

В файле проекта уже подключены всё нужное (версии зависят от версии SDK; для SDK 10.0.300 — такие):

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <IsPackable>false</IsPackable>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="coverlet.collector" Version="6.0.4" />
    <PackageReference Include="Microsoft.NET.Test.Sdk" Version="17.14.1" />
    <PackageReference Include="xunit" Version="2.9.3" />
    <PackageReference Include="xunit.runner.visualstudio" Version="3.1.4" />
  </ItemGroup>

</Project>
```

*   `TargetFramework` — целевой фреймворк: `net10.0` означает, что проект собирается и запускается на .NET 10;
*   `xunit` — сам фреймворк тестирования;
*   `xunit.runner.visualstudio` — интеграция с тестовыми панелями и `dotnet test`;
*   `Microsoft.NET.Test.Sdk` — обвязка для запуска тестов;
*   `coverlet.collector` — сборщик покрытия кода (понадобится в разделе отчётности).

Откройте созданный `UnitTest1.cs`:

```csharp
namespace MyFirstTestProject;

public class UnitTest1
{
    [Fact] // Атрибут xUnit: помечает метод как тест
    public void Test1()
    {
        // Arrange (Подготовка): данные и окружение
        int a = 5;
        int b = 10;

        // Act (Действие): выполняем то, что проверяем
        int result = a + b;

        // Assert (Проверка): сверяем результат с ожиданием
        Assert.Equal(15, result);
    }
}
```

Мы видим классическую структуру теста **AAA**: Arrange — Act — Assert. Подробно её и атрибуты xUnit мы разберём в следующих лекциях.

**Шаг 3. Запуск теста.**

*   Через терминал:
    ```bash
    dotnet test
    ```
*   Или в VS Code: откройте панель **Testing** (иконка колбы), нажмите «Run Tests» — напротив теста появится зелёная галочка.

Пример вывода команды `dotnet test`:

```
Определение проектов для восстановления...
Восстановлен D:\MyFirstTestProject\MyFirstTestProject.csproj (за 150 ms).
...
Сборка успешно завершена.
Тестовый запуск для D:\MyFirstTestProject\bin\Debug\net10.0\MyFirstTestProject.dll
Пройден!  — не пройдено: 0, пройдено: 1, пропущено: 0, всего: 1, длительность: 3 ms
```

Поздравляем: вы настроили рабочее окружение, создали тестовый проект и запустили первый автотест — и в терминале, и в VS Code.

### **Резюме**

1.  **.NET SDK** — фундамент рабочего окружения: сборка, запуск, тестирование и управление пакетами. **.NET Runtime** нужен только для запуска готовых приложений.
2.  Выбирайте **LTS-версии** .NET; актуальная LTS — **.NET 10** (поддержка до ноября 2028 года).
3.  **Visual Studio Code + C# Dev Kit** — лёгкое и бесплатное окружение для C#, встроенный терминал и панель Testing делают редактор полноценным рабочим местом тестировщика.
4.  **NuGet** — система управления зависимостями. Пакеты подключаются через `dotnet add package` и фиксируются в файле `*.csproj`; версии нужно осознанно фиксировать.
5.  Цепочка `SDK → редактор → зависимости → проект` — база, с которой начинается любая автоматизация тестирования на .NET.
6.  Ключевые команды `dotnet new`, `dotnet build`, `dotnet test` понадобятся в каждой практической работе курса.

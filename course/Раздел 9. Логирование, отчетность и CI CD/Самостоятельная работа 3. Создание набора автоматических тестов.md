# Самостоятельная работа 3. Создание набора автоматических тестов

Индивидуальный проект: полный набор автоматических тестов (юнит, интеграционные, API) с логированием, отчётностью и непрерывной интеграцией

## Тема

Создание набора автоматических тестов для индивидуального проекта: юнит-тесты, интеграционные тесты с базой данных SQLite, API-тесты, логирование Serilog, отчётность TRX и CI-пайплайн GitHub Actions.

## Цель

Закрепить и объединить навыки, полученные в разделах 4–9: спроектировать и реализовать полноценный набор автоматических тестов для собственного проекта, настроить отчётность и автоматический запуск проверок в CI.

## Задачи

- Выбрать предметную область и реализовать (или использовать готовое) консольное/библиотечное приложение с бизнес-логикой.
- Разработать юнит-тесты для сервисного слоя (xUnit, параметризация, изоляция).
- Разработать интеграционные тесты бизнес-логики с реальной базой данных SQLite (EF Core).
- Реализовать API поверх бизнес-логики и написать API-тесты (RestSharp).
- Внедрить логирование тестов (Serilog + вывод через `ITestOutputHelper` и консоль).
- Настроить формирование отчётов: TRX и покрытие кода.
- Создать workflow GitHub Actions с запуском всех наборов и публикацией артефактов.
- Оформить README.md с описанием проекта, команд запуска и бейджем CI.

## Ход работы

### 1. Постановка и предметная область

Выберите предметную область (см. список тем в конце работы) и определите сущности, сервисные операции и правила предметной области. Минимальный состав:

- одна основная сущность (например, `Book`, `Product`, `Student`);
- сервис с 4–6 операциями (добавление, получение, изменение состояния, удаление);
- минимум 2 бизнес-правила, приводящих к ошибкам (например, дубликат уникального поля, запрет удаления активной записи).

Создайте решение из трёх проектов:

```
MyProject.sln
├── MyProject/           # библиотека с логикой (net10.0, EF Core SQLite)
├── MyProject.Api/       # minimal API поверх логики
└── MyProject.Tests/     # тесты (xUnit 2.9.3)
```

Добавьте пакеты:

```bash
dotnet add MyProject package Microsoft.EntityFrameworkCore.Sqlite --version 10.0.12
dotnet add MyProject.Tests package Microsoft.EntityFrameworkCore.Sqlite --version 10.0.12
dotnet add MyProject.Tests package Serilog --version 4.4.0
dotnet add MyProject.Tests package Serilog.Sinks.Console --version 6.1.1
dotnet add MyProject.Tests package RestSharp --version 114.0.0
```

### 2. Юнит-тесты сервиса

Напишите не менее 8 юнит-тестов: успешные сценарии, граничные случаи, ошибки. Используйте:

- `[Fact]` и `[Theory]` с `[InlineData]` для параметризации;
- `IDisposable`/конструктор для подготовки состояния (как в практиках раздела 4);
- `Assert.Throws<...>` для проверки исключений;
- Moq — для изоляции от внешних зависимостей (как в практиках раздела 5), если сервис зависит от интерфейсов.

Помните, что юнит-тесты не должны обращаться к реальной базе данных: подключения и внешние сервисы замещаются тестовыми двойниками.

### 3. Интеграционные тесты с SQLite

Создайте отдельный тестовый класс с реальной базой SQLite «в памяти» (подход из практики 27):

```csharp
public class MyServiceSqliteTests : IDisposable
{
    private readonly SqliteConnection _connection;
    private readonly MyDbContext _context;
    private readonly MyService _service;

    public MyServiceSqliteTests()
    {
        _connection = new SqliteConnection("DataSource=:memory:");
        _connection.Open();
        var options = new DbContextOptionsBuilder<MyDbContext>()
            .UseSqlite(_connection)
            .Options;
        _context = new MyDbContext(options);
        _context.Database.EnsureCreated();
        _service = new MyService(_context);
    }

    public void Dispose()
    {
        _context.Dispose();
        _connection.Dispose();
    }
}
```

Обязательно проверьте минимум одно ограничение уровня БД (уникальный индекс, внешний ключ) отдельным тестом. Отметьте интеграционные тесты категорией:

```csharp
[Trait("Category", "integration")]
public class MyServiceSqliteTests { ... }
```

### 4. API и API-тесты

Реализуйте minimal API (2–4 endpoint'а) поверх сервиса. В тестах используйте RestSharp 114:

```csharp
var options = new RestClientOptions(BaseUrl);
var client = new RestClient(options);
var request = new RestRequest("/api/items", Method.Get);
var response = await client.ExecuteAsync<List<ItemResponse>>(request);
response.IsSuccessful.Should().BeTrue();   // или Assert.True(response.IsSuccessful)
```

Напишите 4–6 API-тестов: получение списка, создание записи, обработка ошибки (400/404/409), проверка содержимого ответа. Адрес API берите из переменной окружения (задел для CI):

```csharp
private static string BaseUrl =>
    Environment.GetEnvironmentVariable("MY_API_URL") ?? "http://localhost:5080";
```

### 5. Логирование

Подключите Serilog в тестовом проекте:

```csharp
private readonly ILogger _logger;

public MyServiceTests(ITestOutputHelper output)
{
    _logger = new LoggerConfiguration()
        .MinimumLevel.Debug()
        .WriteTo.Console()
        .WriteTo.Sink(new XunitOutputSink(output))
        .CreateLogger();
}
```

Класс `XunitOutputSink` возьмите из практики 29. Логируйте ключевые шаги тестов (подготовка, действие, ожидание ошибки) на уровнях `Information`/`Warning`.

### 6. Отчётность

Настройте формирование отчётов командами:

```bash
dotnet test --logger "trx;LogFileName=results.trx" --results-directory TestResults
dotnet test --collect:"XPlat Code Coverage" --results-directory TestResults
```

Постройте HTML-отчёт покрытия через ReportGenerator (практика 30) и добейтесь покрытия сервисного слоя не ниже 80%.

### 7. CI: workflow GitHub Actions

Создайте `.github/workflows/ci.yml`. Требования:

- запуск по `push` в `main` и по `pull_request`;
- кэширование NuGet (`actions/cache` с ключом по `hashFiles('**/*.csproj')`);
- матрица минимум по двум наборам: `unit` и `integration` (через `[Trait("Category", ...)]` и `--filter "Category=..."`);
- запуск API-тестов: поднятие API в фоне с ожиданием готовности (как в практике 32) или отдельный job;
- публикация TRX-отчётов артефактами с `if: always()`;
- сводный job, скачивающий все отчёты (`actions/download-artifact`, `merge-multiple: true`);
- бейдж статуса в README.

Пример скелета workflow (дополните по образцу практик 31–33):

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

env:
  DOTNET_VERSION: '10.0.x'

jobs:
  tests:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        suite: [unit, integration]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      - run: dotnet test MyProject.Tests --filter "Category=${{ matrix.suite }}" --logger "trx;LogFileName=${{ matrix.suite }}.trx" --results-directory TestResults
      - if: always()
        uses: actions/upload-artifact@v7
        with:
          name: trx-${{ matrix.suite }}
          path: '**/TestResults/*.trx'
```

Оформите README.md: описание проекта, структура, команды запуска, категории тестов, раздел «CI» с бейджем и скриншотами, результаты покрытия. Загрузите проект в GitHub (публичный репозиторий) и убедитесь, что workflow выполняется успешно.

## Критерии оценки

### Отлично (9-10 баллов)

- Реализованы все три уровня тестов: юнит, интеграционные (SQLite), API.
- Юнит-тесты изолированы, есть параметризация и проверка исключений; ≥ 8 тестов.
- Интеграционные тесты работают с реальной БД SQLite и проверяют ограничение уровня БД.
- API-тесты корректно обрабатывают успешные и ошибочные сценарии.
- Логирование Serilog выводится в консоль и отчёт; есть осмысленные сообщения.
- TRX-отчёт и покрытие ≥ 80% для сервисного слоя; HTML-отчёт построен.
- Workflow: кэш, матрица, артефакты, сводка, бейдж — всё работает, статус зелёный.
- README полный; код структурирован и соответствует соглашениям курса (.NET 10, xUnit 2.9.3, RestSharp 114).

### Хорошо (7-8 баллов)

- Реализованы юнит- и интеграционные тесты; API-тесты упрощены или частичны.
- CI запускает тесты без матрицы; артефакты публикуются, сводка отсутствует.
- Покрытие ниже 80%, но отчёт формируется.
- README содержит основные разделы.

### Удовлетворительно (5-6 баллов)

- Реализованы только юнит-тесты (или юнит + упрощённые API-тесты).
- Workflow запускает тесты одной командой, артефакты не настроены.
- Логирование и отчётность минимальны; README краткий.

### Неудовлетворительно (0-4 баллов)

- Тесты отсутствуют или не выполняются; проект не собирается.
- CI не настроен; работа не загружена в репозиторий.

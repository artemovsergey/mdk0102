# Практическая работа 30. Отчетность в тестах. TRX и артефакты CI

### **Тема**

Формирование отчётности о результатах тестирования: TRX-отчёт, покрытие кода (`XPlat Code Coverage`), HTML-отчёт ReportGenerator и подготовка артефактов для CI.

### **Цель**

- Настроить сохранение TRX-отчёта при запуске тестов.
- Разобраться в структуре TRX: результаты, длительность, вывод и ошибки тестов.
- Измерить покрытие кода тестами с помощью `coverlet`.
- Сгенерировать наглядный HTML-отчёт о покрытии инструментом ReportGenerator.
- Подготовить отчёты как артефакты для CI-пайплайна (закрепляется в практиках 31–33).

### **Теоретическая часть**

**Зачем нужны отчёты.** Консольный вывод `dotnet test` удобен для локальной работы, но не годится для хранения и анализа: он не сохраняется, его нельзя приложить к результатам CI, по нему нельзя отследить историю. Поэтому результат прогона сохраняют в машиночитаемом виде.

| Формат | Назначение | Кто читает |
|--------|-----------|-----------|
| Консоль | Быстрая локальная проверка | Разработчик |
| **TRX** | Полный результат прогона: тесты, длительности, вывод, ошибки | IDE, CI, отчёты Azure DevOps/GitHub |
| JUnit XML | Обмен результатами между системами | CI-серверы (Jenkins, GitLab) |
| Cobertura XML | Покрытие кода (какие строки выполнились) | ReportGenerator, CI |

**Что такое TRX.** TRX (Visual Studio Test Results) — XML-файл с результатами прогона. Основные элементы:

- `<UnitTestResult testName="..." outcome="Passed|Failed|Skipped" duration="...">` — результат одного теста;
- `<Output>` — сохранённый вывод теста (`ITestOutputHelper`);
- `<ErrorInfo>` — сообщение и стек ошибки упавшего теста;
- `<ResultSummary>` — итоги прогона: сколько прошло, упало, пропущено.

TRX создаётся логгером VSTest:

```bash
dotnet test --logger "trx;LogFileName=results.trx" --results-directory TestResults
```

**Покрытие кода (code coverage).** Покрытие показывает, какая доля строк тестируемого кода была выполнена во время прогона. Это не оценка качества тестов, но полезный индикатор «белых пятен»: если критичный метод не покрыт — возможно, для него забыли сценарий.

В шаблоне `dotnet new xunit` уже подключён сборщик покрытия `coverlet.collector`. Достаточно указать сборщик при запуске:

```bash
dotnet test --collect:"XPlat Code Coverage" --results-directory TestResults
```

Рядом с отчётом появится файл `coverage.cobertura.xml` (в подкаталоге с новым GUID).

**ReportGenerator.** XML-файл покрытия читать глазами неудобно. Инструмент `dotnet-reportgenerator-globaltool` превращает его в HTML-отчёт: список классов, процент покрытия по строкам и ветвям, подсветка непокрытых строк.

**Артефакты.** В CI отчёты (TRX, HTML, XML) сохраняют как артефакты workflow — файлы, доступные для скачивания после прогона. Это позволяет разобрать причины падения, не перезапуская тесты. Подробно настраивается в практиках 31–33.

> Allure — популярный фреймворк отчётов в мире Java/Python (красивые шаги, вложения, история). В .NET-проектах чаще обходятся связкой TRX + HTML-отчёт покрытия + встроенный интерфейс CI. Именно такой набор мы и применяем; при желании Allure подключается к любому CI отдельно.

### **Ход работы**

1.  Откройте решение `LibraryApp.sln` из Практической работы 29 (с логированием Serilog).

2.  Запустите тесты с сохранением TRX-отчёта:

    ```bash
    dotnet test --logger "trx;LogFileName=results.trx" --results-directory TestResults
    ```

    Убедитесь, что в каталоге `TestResults` появился файл `results.trx`.

3.  Откройте `results.trx` в VS Code и найдите:
    - элемент `<UnitTestResult>` своего самого длинного теста и его `duration`;
    - элемент `<ResultSummary>` с итоговым количеством тестов.

4.  Посмотрите, как выглядит TRX для упавшего теста. Временно сломайте один тест (неверное ожидаемое значение), повторите запуск и найдите в отчёте элементы `<Output>` и `<ErrorInfo>` у этого теста. Верните тест в рабочее состояние.

5.  Выполните прогон со сбором покрытия:

    ```bash
    dotnet test --collect:"XPlat Code Coverage" --results-directory TestResults
    ```

    Найдите созданный файл `coverage.cobertura.xml` (он лежит в подкаталоге с именем-идентификатором).

6.  Установите ReportGenerator и постройте HTML-отчёт:

    ```bash
    dotnet tool install --global dotnet-reportgenerator-globaltool
    reportgenerator -reports:TestResults/**/coverage.cobertura.xml -targetdir:coveragereport -reporttypes:"Html;TextSummary"
    ```

    Откройте `coveragereport/index.html` в браузере. Изучите проценты покрытия по классам и подсветку непокрытых строк в `LibraryService`.

7.  Дополнительно: исключите из покрытия код, который не имеет смысла измерять в учебном проекте (сущности, контекст). Для этого существует атрибут `[ExcludeFromCodeCoverage]` из пространства имён `System.Diagnostics.CodeAnalysis`, однако проще исключить целые сборки/классы настройкой ReportGenerator:

    ```bash
    reportgenerator -reports:TestResults/**/coverage.cobertura.xml -targetdir:coveragereport -reporttypes:"Html" -classfilters:"-LibraryApp.Book;-LibraryApp.LibraryDbContext"
    ```

    Сравните итоговый процент покрытия до и после фильтрации. Объясните разницу.

8.  Сделайте скриншоты: вывод `dotnet test` с TRX, страница `index.html`. Сохраните их в папку `images`.

9.  Оформите `README.md` и зафиксируйте изменения:

    ```bash
    git add -A
    git commit -m "docs: TRX-отчет и отчет покрытия ReportGenerator"
    git push
    ```

### **Практический пример**

**Команда прогона с TRX-отчётом:**

```bash
dotnet test --logger "trx;LogFileName=results.trx" --results-directory TestResults
```

**Фрагмент созданного `TestResults/results.trx`:**

```xml
<UnitTestResult executionId="..." testId="..." testName="LibraryApp.Tests.LibraryServiceTests.AddBookAsync_ValidBook_SavesToDatabase"
                computerName="..." duration="00:00:00.1040000" outcome="Passed">
  <Output>
    <StdOut>[14:53:15 INF] Добавляем книгу CLR via C# (ISBN 978-5-496-01202-5)
[14:53:15 INF] Книг в базе после добавления: 1</StdOut>
  </Output>
</UnitTestResult>
```

**Фрагмент TRX упавшего теста:**

```xml
<UnitTestResult testName="LibraryApp.Tests.FailDemoTests.Demo_Fails" duration="00:00:00.0040000" outcome="Failed">
  <Output>
    <StdOut>ДИАГНОСТИКА: вывод упавшего теста через ITestOutputHelper</StdOut>
    <ErrorInfo>
      <Message>демонстрационное падение</Message>
      <StackTrace>   at LibraryApp.Tests.FailDemoTests.Demo_Fails() in ...\FailDemoTests.cs:line 16</StackTrace>
    </ErrorInfo>
  </Output>
</UnitTestResult>
```

**Команды покрытия и отчёта:**

```bash
dotnet test --collect:"XPlat Code Coverage" --results-directory TestResults

dotnet tool install --global dotnet-reportgenerator-globaltool

reportgenerator -reports:TestResults/**/coverage.cobertura.xml -targetdir:coveragereport -reporttypes:"Html;TextSummary"
```

**Фрагмент `coveragereport/Summary.txt` (реальный результат эталонного проекта):**

```
Summary
  Generated on: 21.09.2026 - 14:54:25
  Coverage date: 21.09.2026 - 14:53:15
  Parser: MultiReport (2x Cobertura)
  Assemblies: 1
  Classes: 3
  Files: 3
  Line coverage: 93.8%
  Covered lines: 46
  Uncovered lines: 3
  Coverable lines: 49
  Total lines: 90
```

Пояснения к цифрам:

- `Line coverage` — доля выполненных строк из всех измеримых (`Covered / Coverable`);
- `Assemblies: 1, Classes: 3` — измеряются `LibraryService`, `Book`, `LibraryDbContext`; исключив последние два фильтром, вы получите «чистое» покрытие сервиса;
- `Parser: MultiReport (2x Cobertura)` — ReportGenerator нашёл два XML-файла покрытия (остались от разных прогонов). Чтобы отчёт строился по одному прогону, удаляйте каталог `TestResults` перед запуском или указывайте точный путь к последнему файлу.

**Важный приём для CI.** Отчёт о тестах публикуется даже при падении тестов — иначе он потеряется. В GitHub Actions для этого у шага публикации ставится условие `if: always()` (подробно в практиках 31–33):

```yaml
- name: Публикация отчёта
  if: always()
  uses: actions/upload-artifact@v7
  with:
    name: test-results
    path: '**/TestResults/*.trx'
```

**Вариант 3.** Отчёт покрытия с фильтром исключения сущностей и контекста; сравнить процент покрытия до и после фильтрации.

**Вариант 5.** Прогнать тесты в конфигурации Release (`dotnet test -c Release`) с TRX; сравнить длительности тестов с Debug-прогоном и объяснить различие.

**Вариант 6.** TRX + покрытие; исключить из покрытия `Book` и `LibraryDbContext`; добиться покрытия `LibraryService` ≥ 90%.

**Вариант 7.** Прогнать тесты с фильтром (`--filter "FullyQualifiedName~Borrow"`), сохранить отдельный TRX; убедиться, что в отчёте только отобранные тесты.

**Вариант 8.** TRX + покрытие; подготовить команды для CI (прогон, отчёт, публикация артефакта) в виде отдельного файла `docs/ci-commands.md`.

**Вариант 9.** TRX + покрытие; добавить в проект класс с намеренно непокрытым методом и показать его в HTML-отчёте (непокрытые строки красным).

**Вариант 10.** TRX + покрытие; настроить вывод отчёта в папку `artifacts/` и добавить её в `.gitignore` (отчёты не коммитятся).

**Вариант 11.** Сделать два прогона с TRX (до и после добавления нового теста), сравнить `<ResultSummary>`: количество и длительность.

**Вариант 12.** TRX + покрытие; составить таблицу покрытия по методам сервиса (из HTML-отчёта) с выводом о «белых пятнах».

**Вариант 13.** TRX + покрытие; сымитировать падение и показать, что TRX сохраняется с `outcome="Failed"` и `<ErrorInfo>`.

**Вариант 14.** TRX + покрытие; добиться 100% покрытия `LibraryService`, добавив недостающие тесты.

**Вариант 15.** TRX + покрытие; оформить в README раздел «Отчётность» с командами и скриншотами обоих отчётов.

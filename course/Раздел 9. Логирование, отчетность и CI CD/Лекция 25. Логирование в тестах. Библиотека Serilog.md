### **Подробное рассмотрение каждого пункта плана**

#### **1. Зачем логировать выполнение тестов**

**Подробное объяснение:**

Юнит-тест либо прошёл, либо упал. Если он упал в CI на чужой машине, у вас нет отладчика — есть только сообщение об ошибке. Но одного сообщения часто недостаточно:

```
Assert.Equal() Failure: Values differ
Expected: 3
Actual:   2
```

Что произошло до этого? Сколько книг было в базе? Какой метод вернул неверное значение? Лог выполнения теста отвечает на эти вопросы:

- **диагностика в CI** — лог единственный «свидетель» падения;
- **история прогона** — видно порядок шагов, входные данные, промежуточные результаты;
- **воспроизведение** — лог показывает состояние, при котором тест упал;
- **замеры** — отметки времени помогают найти медленные места.

| Что стоит логировать в тестах | Что логировать не нужно |
|-------------------------------|--------------------------|
| Начало и конец сценария | Каждую строку кода |
| Входные данные (идентификаторы, роли) | Полные объекты с вложенными связями |
| Ключевые бизнес-события («книга выдана») | Ожидаемые/фактические значения всех assert |
| Исключения целиком (`Exception.ToString()`) | Пароли, токены, персональные данные |

---

#### **2. Уровни логирования**

**Подробное объяснение:**

Уровень (level) показывает важность сообщения. Настраивая минимальный уровень, можно «отсечь» лишний шум, не меняя код.

| Уровень | Смысл | Пример в тестах |
|---------|-------|-----------------|
| `Verbose` | Максимальная детализация | Значения каждой переменной в цикле |
| `Debug` | Отладочная информация | «Создано подключение к БД в памяти» |
| `Information` | Нормальный ход событий | «Тест выполнен: 10 книг добавлено» |
| `Warning` | Нештатная, но ожидаемая ситуация | «Дубликат ISBN — тест проверяет ошибку» |
| `Error` | Ошибка операции | «Не удалось сохранить книгу» |
| `Fatal` | Приложение не может продолжать работу | «База данных недоступна» |

Правила:

- в обычном прогоне включают `Information` и выше — лог читаемый;
- при отладке понижают порог до `Debug`/`Verbose`;
- `Warning` не повод падать, а `Error` не всегда означает, что тест обязан упасть: тест может *проверять*, что ошибка обработана.

#### **3. Структурированные логи**

**Подробное объяснение:**

Классическая ошибка — склеивать сообщение строкой:

```csharp
// Плохо: в логе только текст, машине его не разобрать
_logger.Information($"Книга {bookId} выдана читателю {readerId}");
```

Структурированный лог сохраняет данные отдельными полями:

```csharp
// Хорошо: BookId и ReaderId — отдельные свойства события
_logger.Information("Книга {BookId} выдана читателю {ReaderId}", bookId, readerId);
```

В консоли обе строки выглядят одинаково, но во втором случае система хранит событие как набор «имя — значение»:

```
{ "Level": "Information", "Message": "Книга 7f3a... выдана читателю 2b91...",
  "BookId": "7f3a...", "ReaderId": "2b91..." }
```

Что это даёт:

- **фильтрация** — «показать все события с `BookId = 7f3a...`»;
- **агрегация** — «сколько выдач книг было за час»;
- **анализ** — сбор в Elasticsearch, Seq, Grafana Loki без разбора текста.

Важно: заполнители `{BookId}` — это **не** интерполяция строк и не форматирование. Нельзя писать `{bookId}` с выражением внутри или использовать `$"..."` вместо аргументов — вы потеряете структуру.

#### **4. Обзор библиотек: log4net, NLog, Microsoft.Extensions.Logging**

**Подробное объяснение:**

| Библиотека | Конфигурация | Сильные стороны | Где встречается |
|------------|--------------|-----------------|-----------------|
| `log4net` | XML (`log4net.config`) | Классика, лёгкая встраиваемость | Legacy-проекты |
| `NLog` | XML / JSON / код | Гибкие правила маршрутизации | ERP, desktop |
| `Microsoft.Extensions.Logging` | код / `appsettings.json` | Встроена в .NET, абстракция `ILogger<T>` | ASP.NET Core, библиотеки |
| `Serilog` | код / JSON | Структурированные логи, sinks, шаблоны | Современные проекты |

**`Microsoft.Extensions.Logging`** — стандартная абстракция .NET. Класс получает `ILogger<T>` через конструктор, а провайдер (консоль, файл, Serilog) подключается снаружи:

```csharp
public class LibraryService
{
    private readonly ILogger<LibraryService> _logger;

    public LibraryService(ILogger<LibraryService> logger) => _logger = logger;
}
```

Это правильный подход для **тестируемого кода**: он зависит от абстракции, а не от конкретной библиотеки. В тестах абстракцию можно заменить на заглушку или на реальный логгер.

**`log4net`** долгое время был стандартом де-факто, но в новых проектах его почти не выбирают: настройка через XML-файл, нет структурированных логов «из коробки». `NLog` похож, но удобнее в конфигурации.

**`Serilog`** — сегодня самый популярный выбор в .NET: событие лога — это объект с полями, а приёмники (sinks) определяют, куда его записать. Именно с ним мы будем работать.

#### **5. Serilog: конфигурация и приёмники (sinks)**

**Подробное объяснение:**

Установка пакетов:

```bash
dotnet add package Serilog --version 4.4.0
dotnet add package Serilog.Sinks.Console --version 6.1.1
dotnet add package Serilog.Sinks.File --version 7.0.0
```

Минимальная конфигурация:

```csharp
using Serilog;

Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .WriteTo.Console()
    .CreateLogger();

Log.Information("Запущено тестов: {TestCount}", 10);
Log.Debug("Подключение к базе данных создано");

Log.CloseAndFlush();
```

Разберём строки:

1. `new LoggerConfiguration()` — конструктор конфигурации логгера;
2. `.MinimumLevel.Debug()` — записывать всё от `Debug` и выше;
3. `.WriteTo.Console()` — приёмник: выводить в консоль;
4. `.CreateLogger()` — собрать логгер; результат присваивается глобальному `Log.Logger`;
5. `Log.Information(...)` — статический фасад для записи;
6. `Log.CloseAndFlush()` — сбросить буферы (важно при записи в файл и в конце работы приложения).

**Приёмник (sink)** — это «получатель» событий. Один логгер может писать сразу в несколько мест:

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .WriteTo.Console()
    .WriteTo.File("logs/tests-.log")
    .CreateLogger();
```

Популярные приёмники:

| Sink | Куда пишет | Пакет |
|------|-----------|-------|
| Console | Консоль | `Serilog.Sinks.Console` |
| File | Файл с ротацией | `Serilog.Sinks.File` |
| Seq | Веб-интерфейс для поиска логов | `Serilog.Sinks.Seq` |
| Elasticsearch | Поисковый движок | `Serilog.Sinks.Elasticsearch` |
| Debug | Окно Output в отладчике | `Serilog.Sinks.Debug` |

Понижение уровня для «шумных» источников:

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .MinimumLevel.Override("Microsoft", Serilog.Events.LogEventLevel.Warning)
    .WriteTo.Console()
    .CreateLogger();
```

Здесь всё от `Microsoft.*` (инфраструктурные логи ASP.NET Core, EF Core) будет записываться только при уровне `Warning` и выше — полезно, чтобы не утонуть в SQL-запросах.

#### **6. Шаблоны вывода и запись в файл**

**Подробное объяснение:**

Внешний вид строки в консоли задаётся **шаблоном вывода** (output template):

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .WriteTo.Console(
        outputTemplate: "[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj}{NewLine}{Exception}")
    .WriteTo.File(
        path: "logs/tests-.log",
        rollingInterval: RollingInterval.Day,
        outputTemplate: "{Timestamp:yyyy-MM-dd HH:mm:ss.fff} [{Level:u3}] {Message:lj}{NewLine}{Exception}")
    .CreateLogger();
```

Популярные токены шаблона:

| Токен | Значение | Пример вывода |
|-------|----------|---------------|
| `{Timestamp:HH:mm:ss}` | Время события | `14:32:05` |
| `{Level:u3}` | Уровень, 3 символа | `INF`, `WRN`, `ERR` |
| `{Message:lj}` | Текст + свойства (literal/json) | `Книга выдана` |
| `{NewLine}` | Перевод строки | — |
| `{Exception}` | Стек исключения | `System.InvalidOperationException...` |
| `{Properties}` | Все свойства события | `BookId: "..."` |

`rollingInterval: RollingInterval.Day` создаёт файл на каждый день: `tests-20260921.log`. При ротации Serilog сам следит за размером и количеством файлов (`retainedFileCountLimit`), что важно, чтобы тестовый прогон не заполнил диск.

Проверить конфигурацию без запуска тестов можно так:

```bash
dotnet run --project LibraryApp.Tests
```

и посмотреть появившийся файл `logs/tests-<дата>.log`.

#### **7. Логирование в тестах xUnit: ITestOutputHelper**

**Подробное объяснение:**

Первое, с чем сталкивается каждый: **`Console.WriteLine` в xUnit не виден**. Он не попадает ни в отчёт `dotnet test`, ни в TRX-файл. Для вывода из теста используется `ITestOutputHelper` из `Xunit.Abstractions`:

```csharp
using Xunit;
using Xunit.Abstractions;

public class OutputDemoTests
{
    private readonly ITestOutputHelper _output;

    public OutputDemoTests(ITestOutputHelper output) => _output = output;

    [Fact]
    public void Test_ShouldWriteToOutput()
    {
        _output.WriteLine("Тест начался");
        _output.WriteLine("Тест завершился");
    }
}
```

xUnit внедряет `ITestOutputHelper` сам: достаточно объявить параметр конструктора. Записи видны:

- в консоли — при запуске `dotnet test --logger "console;verbosity=detailed"`;
- в TRX-отчёте — в секции `Output` каждого теста (лекция 30);
- в интерфейсе CI — как вложение к тесту.

Чтобы отправлять в этот вывод **логи Serilog**, самый простой способ — написать собственный sink. Он маленький, но демонстрирует главную идею Serilog: sink — это просто класс, реализующий `ILogEventSink`.

```csharp
using Serilog.Core;
using Serilog.Events;
using Xunit.Abstractions;

/// <summary>Sink, который выводит события Serilog в отчёт xUnit.</summary>
public class XunitOutputSink : ILogEventSink
{
    private readonly ITestOutputHelper _output;

    public XunitOutputSink(ITestOutputHelper output) => _output = output;

    public void Emit(LogEvent logEvent)
    {
        _output.WriteLine($"[{logEvent.Level:u3}] {logEvent.RenderMessage()}");

        if (logEvent.Exception is not null)
        {
            _output.WriteLine(logEvent.Exception.ToString());
        }
    }
}
```

Подключение в тестовом классе:

```csharp
using Serilog;
using Xunit;
using Xunit.Abstractions;

public class LibraryServiceTests
{
    private readonly ILogger _logger;

    public LibraryServiceTests(ITestOutputHelper output)
    {
        _logger = new LoggerConfiguration()
            .MinimumLevel.Debug()
            .WriteTo.Console()
            .WriteTo.Sink(new XunitOutputSink(output))
            .CreateLogger();
    }

    [Fact]
    public void Logging_ShouldBeVisibleInTestOutput()
    {
        _logger.Information("Начало теста: {TestName}", nameof(Logging_ShouldBeVisibleInTestOutput));

        // ... проверки ...

        _logger.Information("Тест завершён успешно");
    }
}
```

Обратите внимание: логгер создаётся **в конструкторе класса тестов**, а не через глобальный `Log.Logger`. Причина — xUnit запускает классы тестов параллельно, и общий статический логгер смешал бы вывод разных тестов в один поток. Экземпляр `ILogger` на класс решает проблему.

> Существует готовый пакет `Serilog.Sinks.XUnit`, который делает то же самое. Мы написали sink сами, чтобы увидеть механизм изнутри: приёмник — это обычный класс с методом `Emit`.

Того же принципа придерживается и тестируемый код:

```csharp
// В сервисе — абстракция Microsoft.Extensions.Logging
public LibraryService(LibraryDbContext context, ILogger<LibraryService> logger) { ... }

// В тесте абстракцию легко заменить заглушкой (Moq) или настоящим логгером
var service = new LibraryService(context, NullLogger<LibraryService>.Instance);
```

`NullLogger<T>` из пакета `Microsoft.Extensions.Logging.Abstractions` — «пустой» логгер: удобен, когда логирование в конкретном тесте не проверяется.

#### **8. Безопасность и гигиена логов**

**Подробное объяснение:**

Лог — это данные, которые надолго оседают в файлах, CI-артефактах и внешних системах. К ним применимы жёсткие правила:

**Что НИКОГДА не попадает в лог:**

- пароли, PIN-коды, секреты, API-ключи и токены;

- номера банковских карт, паспортные данные;

- персональные данные (адреса, телефоны) без необходимости;

- строки подключения целиком (может содержать пароль);

- содержимое запросов с секретами (заголовок `Authorization`).

**Правила гигиены:**

1. Логируйте **идентификаторы**, а не чувствительные значения: `UserId`, но не `Email`, если можно обойтись идентификатором.
2. Маскируйте данные, если без них не обойтись: `****1234`.
3. Помните, что в CI артефакты доступны всей команде: лог утечки — это утечка.
4. Не логируйте «на всякий случай»: избыточные логи мешают искать настоящую причину.
5. Уровень `Debug` в production обычно выключен — но не полагайтесь на это как на защиту.

### **Резюме**

1.  Логирование в тестах — единственный источник информации о том, **что происходило** до падения, особенно в CI, где нет отладчика.

2.  Уровни (`Verbose`–`Fatal`) позволяют управлять детализацией без правки кода: настраивается минимальный порог.

3.  Структурированные логи сохраняют данные отдельными полями (`{BookId}` вместо `$"..."`), что даёт фильтрацию и агрегацию машинным способом.

4.  `Microsoft.Extensions.Logging` с `ILogger<T>` — стандартная абстракция для тестируемого кода; конкретная библиотека (Serilog) подключается снаружи.

5.  Serilog настраивается кодом: `LoggerConfiguration` → `MinimumLevel` → `WriteTo` (sinks) → `CreateLogger()`. Sink — это приёмник вывода: консоль, файл, Seq и другие.

6.  Шаблон вывода (`outputTemplate`) и ротация файлов (`rollingInterval`) управляют форматом и хранением логов.

7.  В xUnit вывод идёт через `ITestOutputHelper`; логи Serilog попадают туда либо через собственный sink (`ILogEventSink`), либо через пакет `Serilog.Sinks.XUnit`. Логгер создаётся на класс тестов — из-за параллельного запуска.

8.  В логи не попадают секреты, пароли и персональные данные: артефакты CI, файлы и внешние системы хранят их долго.

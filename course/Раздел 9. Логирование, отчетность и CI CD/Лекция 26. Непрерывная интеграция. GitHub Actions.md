### **Подробное рассмотрение каждого пункта плана**

#### **1. Что такое непрерывная интеграция (CI)**

**Подробное объяснение:**

**Непрерывная интеграция (Continuous Integration, CI)** — практика, при которой каждый разработчик часто (несколько раз в день) сливает свою работу в общую ветку, а каждая такая попытка автоматически проверяется: проект собирается, запускаются тесты, выполняется анализ качества.

Проблема, которую решает CI, выглядит так:

```
Разработчик А две недели пишет фичу в своей ветке.
Разработчик Б всё это время менял общий код.
В день слияния: «всё сломалось» — конфликты, падающие тесты,
несовместимые изменения. Разбираться придётся дни.
```

При непрерывной интеграции обратная связь приходит через минуты:

```
Коммит → push → CI автоматически: сборка → тесты → отчёт
              ├─ успех: можно продолжать
              └─ ошибка: разработчик узнаёт первым, пока ущерб мал
```

Ключевые принципы:

- **единый источник правды** — общая ветка (`master`/`main`) всегда собирается и проходит тесты;
- **автоматизация** — никаких «запущу тесты потом вручную»: это делает сервер;
- **быстрая обратная связь** — чем раньше найден дефект, тем дешевле исправление;
- **честный статус** — красный значок на коммите видит вся команда.

Родственные практики:

| Аббревиатура | Название | Что автоматизирует |
|--------------|----------|--------------------|
| CI | Continuous Integration | сборку и тесты при каждом изменении |
| CD | Continuous Delivery | доставку готовой сборки в среду (staging) |
| CD | Continuous Deployment | автоматический выпуск в production |

CI — фундамент: без стабильной сборки и тестов автоматический деплой смысла не имеет.

#### **2. Обзор платформ: GitHub Actions, Jenkins, GitLab CI**

**Подробное объяснение:**

| Платформа | Где выполняется | Конфигурация | Особенности |
|-----------|-----------------|--------------|-------------|
| **GitHub Actions** | Облако GitHub | YAML в `.github/workflows/` | Бесплатно для публичных репозиториев, огромный магазин готовых действий |
| **Jenkins** | Свой сервер | `Jenkinsfile` (Groovy) + плагины | Гибкость, требует администрирования |
| **GitLab CI** | Облако или свой сервер | `.gitlab-ci.yml` | Встроен в GitLab, удобные окружения и реестр образов |

**GitHub Actions** — стандарт для проектов на GitHub: конфигурация лежит в репозитории рядом с кодом, запуск происходит в облаке, инфраструктуру поддерживает GitHub. Для публичных репозиториев минуты выполнения не ограничены, для приватных — есть бесплатный лимит.

**Jenkins** — исторически самый распространённый self-hosted CI-сервер. Его плюс — полный контроль и тысячи плагинов; минус — сервер нужно устанавливать, обновлять, защищать и следить за ним. Встречается на предприятиях, где нельзя выносить код в облако.

**GitLab CI** — аналог GitHub Actions для GitLab: файл `.gitlab-ci.yml`, концепции stages и jobs. Работает и в облаке, и на собственном сервере.

Отдельно стоит **Allure** — не система CI, а фреймворк отчётов о тестировании: строит наглядный HTML-отчёт со шагами, вложениями, историей. Он подключается к любой CI-системе. В нашем курсе мы используем более простой и «родной» для .NET путь: TRX-отчёты и артефакты GitHub Actions (лекция 30).

В этой лекции и практиках работаем с **GitHub Actions**.

#### **3. Анатомия workflow GitHub Actions**

**Подробное объяснение:**

**Workflow** — файл с расширением `.yml` в каталоге `.github/workflows/` репозитория. Каждый файл — независимый сценарий автоматизации.

Минимальный рабочий пример:

```yaml
name: CI

on:
  push:
    branches: [ master ]
  pull_request:
    branches: [ master ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: '10.0.x'

      - name: Запуск тестов
        run: dotnet test
```

Структура файла:

| Ключ | Значение | Обязателен |
|------|----------|------------|
| `name` | Название workflow (видно в интерфейсе GitHub) | Нет |
| `on` | Триггеры: когда запускать | Да |
| `jobs` | Набор заданий | Да |
| `jobs.<id>` | Идентификатор задания (`build`) | Да |
| `jobs.<id>.runs-on` | Какая машина выполняет | Да |
| `jobs.<id>.steps` | Последовательность шагов | Да |
| `steps[].uses` | Готовое действие из магазина | — |
| `steps[].run` | Команда в оболочке | — |

Обратите внимание: YAML — **чувствителен к отступам**, пробелы (не табуляции!) образуют структуру. Ошибка в отступе — ошибка разбора файла.

Шаг `actions/checkout@v7` скачивает код репозитория на машину, `actions/setup-dotnet@v6` устанавливает нужную версию .NET SDK. После них доступна команда `dotnet test`.

#### **4. Триггеры запуска**

**Подробное объяснение:**

События указываются в секции `on`:

```yaml
on:
  # при push в указанные ветки
  push:
    branches: [ master, 'feature/**' ]

  # при открытии/обновлении pull request
  pull_request:
    branches: [ master ]

  # запуск вручную из интерфейса GitHub
  workflow_dispatch:

  # по расписанию: каждый день в 03:00 UTC
  schedule:
    - cron: '0 3 * * *'
```

| Триггер | Когда срабатывает | Типичное применение |
|---------|-------------------|---------------------|
| `push` | После отправки коммитов | Проверка основной ветки |
| `pull_request` | При создании/обновлении PR | Не пустить плохой код в master |
| `workflow_dispatch` | Вручную, кнопкой | Повторный запуск, отладка |
| `schedule` | По cron-расписанию | Ночные регрессионные прогоны |
| `release` | При публикации релиза | Сборка пакета версии |

Фильтры `paths` позволяют не запускать проверку, если изменилась только документация:

```yaml
on:
  push:
    paths-ignore:
      - 'docs/**'
      - '*.md'
```

Совет: настраивайте `pull_request` — именно этот триггер делает CI полезным: он не пропускает сломанные изменения в основную ветку.

#### **5. Jobs, steps и runners**

**Подробное объяснение:**

**Job (задание)** — группа шагов, выполняемых на одной машине. По умолчанию несколько job'ов внутри workflow запускаются **параллельно**. Управление порядком — через `needs`:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: '10.0.x'
      - name: Сборка
        run: dotnet build

  test:
    needs: build          # запустится только после успеха build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: '10.0.x'
      - name: Тесты
        run: dotnet test
```

**Step (шаг)** — атомарная операция: либо `run` (команда оболочки), либо `uses` (готовое действие). Шаги выполняются последовательно; если шаг упал, остальные (по умолчанию) не выполняются.

Важная деталь: **каждый job выполняется на чистой машине**. Это значит, что внутри job'а нельзя рассчитывать на файлы, созданные в другом job'е, — для передачи данных существуют артефакты (пункт 7).

**Runner (раннер)** — машина, которая выполняет job:

| Раннер | Описание |
|--------|----------|
| `ubuntu-latest` | Linux, самый быстрый и дешёвый — типовой выбор |
| `windows-latest` | Windows |
| `macos-latest` | macOS |
| self-hosted | Ваш собственный сервер |

Для учебных проектов почти всегда достаточно `ubuntu-latest`: код .NET кроссплатформенный, тесты на SQLite и Selenium работают на Linux.

#### **6. Матрица и кэширование**

**Подробное объяснение:**

**Матрица (matrix)** запускает один и тот же job с разными параметрами — например, на разных ОС или версиях SDK:

```yaml
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ ubuntu-latest, windows-latest ]
        dotnet: [ '8.0.x', '10.0.x' ]
    runs-on: ${{ matrix.os }}

    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: ${{ matrix.dotnet }}
      - run: dotnet test
```

Этот job превратится в 4 параллельных выполнения (2 ОС × 2 версии SDK). Параметр `fail-fast: false` означает, что падение одной комбинации не отменяет остальные — удобно, чтобы сразу увидеть полную картину.

**Кэширование** ускоряет прогоны: повторно скачанные NuGet-пакеты лежат в кэше и не загружаются заново. `actions/setup-dotnet@v6` умеет кэшировать автоматически:

```yaml
- uses: actions/setup-dotnet@v6
  with:
    dotnet-version: '10.0.x'
    cache: true
    cache-dependency-path: '**/*.csproj'
```

Более общий способ — `actions/cache@v6`:

```yaml
- uses: actions/cache@v6
  with:
    path: ~/.nuget/packages
    key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}
    restore-keys: ${{ runner.os }}-nuget-
```

Как это работает:

- **key** — уникальный идентификатор кэша; включает ОС и хэш файлов проектов;
- при изменении `.csproj` (например, добавили пакет) хэш меняется — кэш создаётся заново;
- **restore-keys** — запасной вариант: если точного совпадения нет, берётся ближайший кэш, который потом обновится.

Экономия заметна сразу: установка пакетов для тестового проекта сокращается с десятков секунд до единиц.

#### **7. Артефакты и секреты**

**Подробное объяснение:**

**Артефакты** — файлы, которые workflow сохраняет для просмотра и скачивания. Типичный пример — отчёты о тестах:

```yaml
- name: Тесты с TRX-отчётом
  run: dotnet test --logger "trx;LogFileName=results.trx" --results-directory TestResults

- name: Сохранить отчёт
  if: always()        # сохранить даже если тесты упали
  uses: actions/upload-artifact@v7
  with:
    name: test-results
    path: TestResults/*.trx
    retention-days: 7
```

Обратите внимание на `if: always()` — без него шаг не выполнится после падения тестов, и самый ценный артефакт (отчёт об ошибке) будет потерян.

Скачать артефакт можно из интерфейса GitHub: страница workflow → раздел **Artifacts**. В другом job'е файл забирается действием `actions/download-artifact@v8`:

```yaml
- uses: actions/download-artifact@v8
  with:
    name: test-results
    path: TestResults
```

**Секреты** — зашифрованные значения, доступные workflow (токены, пароли, строки подключения):

- задаются в репозитории: **Settings → Secrets and variables → Actions → New repository secret**;
- используются подстановкой `${{ secrets.ИМЯ }}`;
- **никогда не выводятся в лог**: GitHub замаскирует точное значение, но собранные из него строки могут утечь.

```yaml
- name: Деплой с токеном
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}
  run: ./scripts/deploy.sh
```

Правила безопасности:

1. Не хранить секреты в файлах репозитория — только в Secrets.
2. Не печатать секреты (`echo`, логи) — маскировка не абсолютна.
3. Для учебных тестов секреты обычно не нужны вовсе.
4. Помнить: секреты **не** передаются в workflow, запущенные из fork'ов, — поэтому неожиданный `secrets.X` пуст именно в PR из чужого репозитория.

#### **8. Бейджи и разбор полного workflow**

**Подробное объяснение:**

**Бейдж (badge)** — значок статуса в README. Он честно показывает всем, проходит ли проект проверки. Адрес имеет формат:

```
https://github.com/ВЛАДЕЛЕЦ/РЕПОЗИТОРИЙ/actions/workflows/ИМЯ_ФАЙЛА/badge.svg
```

В README бейдж вставляется ссылкой:

```markdown
[![CI](https://github.com/artemovsergey/mdk0102/actions/workflows/ci.yml/badge.svg)](https://github.com/artemovsergey/mdk0102/actions/workflows/ci.yml)
```

Соберём всё изученное в один реалистичный workflow `ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [ master ]
  pull_request:
    branches: [ master ]
  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Получение кода
        uses: actions/checkout@v7

      - name: Установка .NET SDK 10
        uses: actions/setup-dotnet@v6
        with:
          dotnet-version: '10.0.x'
          cache: true
          cache-dependency-path: '**/*.csproj'

      - name: Восстановление пакетов
        run: dotnet restore

      - name: Сборка
        run: dotnet build --no-restore --configuration Release

      - name: Тесты
        run: dotnet test --no-build --configuration Release --logger "trx;LogFileName=results.trx" --results-directory TestResults

      - name: Публикация отчёта
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: test-results
          path: TestResults/*.trx
          retention-days: 7
```

Что здесь происходит по шагам:

1. `checkout` — код попадает на раннер;
2. `setup-dotnet` — ставится SDK 10 с кэшем NuGet;
3. `restore` и `build` — проект собирается в Release;
4. `test` — тесты запускаются с TRX-отчётом;
5. `upload-artifact` — отчёт сохраняется даже при падении тестов.

Флаги `--no-restore` и `--no-build` экономят время: команды уже выполнили соответствующую работу.

Итог: при каждом push и pull request GitHub автоматически собирает проект и прогоняет тесты; результат виден в интерфейсе, статус — в бейдже README, отчёт — в артефактах. Это и есть непрерывная интеграция в действии.

### **Резюме**

1.  Непрерывная интеграция — практика частого слияния изменений с автоматической проверкой каждой попытки: сборка, тесты, отчёты.

2.  CI-платформа запускает проверки в облаке или на своём сервере. GitHub Actions — облачная и бесплатная для публичных репозиториев; Jenkins и GitLab CI — альтернативы; Allure — инструмент отчётов, а не CI.

3.  Workflow — YAML-файл в `.github/workflows/`, состоящий из триггеров (`on`) и заданий (`jobs`).

4.  Триггеры определяют, когда запускать: `push`, `pull_request`, `workflow_dispatch`, `schedule`, `release`.

5.  Job — набор последовательных шагов на одной машине (runner); jobs по умолчанию параллельны, порядок задаётся через `needs`.

6.  Матрица запускает один job с разными параметрами (ОС, версии SDK), кэш (`actions/cache@v6` или `cache: true` в setup-dotnet) ускоряет повторные прогоны.

7.  Артефакты сохраняют отчёты и другие файлы (`upload-artifact`/`download-artifact`), секреты хранят чувствительные значения и не попадают в логи.

8.  Минимальный полезный workflow: checkout → setup-dotnet → build → test → artifact; статус проекта отражает бейдж в README.

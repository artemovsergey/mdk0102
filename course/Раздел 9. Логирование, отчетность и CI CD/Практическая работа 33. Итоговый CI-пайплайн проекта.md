# Практическая работа 33. Итоговый CI-пайплайн проекта

### **Тема**

Построение итогового CI-пайплайна: кэширование пакетов NuGet, матричный запуск наборов тестов по категориям, сводные артефакты и бейдж статуса в README.

### **Цель**

- Собрать проверенный пайплайн из практик 31–32 в единый workflow.
- Настроить кэширование NuGet-пакетов между запусками.
- Разделить тесты на категории через `[Trait]` и запускать их матрицей.
- Сформировать сводку результатов и добавить бейдж CI в README.

### **Теоретическая часть**

**Кэширование NuGet.** При каждом запуске runner скачивает пакеты заново — это десятки секунд и лишняя нагрузка. Каталог глобального кэша (`~/.nuget/packages`) сохраняют действием `actions/cache`. Ключ кэша привязывают к содержимому файлов проектов через `hashFiles('**/*.csproj')`: если зависимости не менялись — кэш переиспользуется, если изменились — создаётся новый:

```yaml
- uses: actions/cache@v6
  with:
    path: ~/.nuget/packages
    key: nuget-${{ runner.os }}-${{ hashFiles('**/*.csproj') }}
    restore-keys: |
      nuget-${{ runner.os }}-
```

**Категории тестов и матрица.** В xUnit категория задаётся атрибутом `[Trait("Category", "unit")]`. Тогда набор можно запускать фильтром `--filter "Category=unit"`. Матрица запускает один и тот же job несколько раз с разными параметрами — например, по одному значению на категорию:

```yaml
strategy:
  fail-fast: false        # не отменять остальные наборы при падении одного
  matrix:
    suite: [unit, integration, api]
```

Значение подставляется через `${{ matrix.suite }}`. Свойство `fail-fast: false` важно: падение юнит-тестов не должно скрыть результаты интеграционных.

**Сводка и артефакты.** Каждый матричный запуск публикует собственный артефакт с уникальным именем (`trx-${{ matrix.suite }}`). Итоговый job `summary` с действием `actions/download-artifact` (параметры `pattern: trx-*`, `merge-multiple: true`) собирает все отчёты в один каталог — так результаты доступны одним архивом. Условие `if: always()` гарантирует, что сводка выполнится, даже если тесты падали.

**Бейдж.** Статус workflow отображается бейджем в README. Разметка:

```markdown
![CI](https://github.com/USER/REPO/actions/workflows/ci.yml/badge.svg)
```

Бейдж перекрашивается автоматически: зелёный — последний запуск успешен, красный — упал. Публичный репозиторий не требует токена для отображения бейджа.

### **Ход работы**

1.  Откройте проект из практик 31–32. Разметьте тесты категориями:

    ```csharp
    // LibraryApp.Tests/LibraryServiceTests.cs
    [Trait("Category", "unit")]
    public class LibraryServiceTests { ... }
    ```

    Интеграционные тесты (с SQLite) отметьте `integration`, API-тесты — `api`.

2.  Убедитесь, что фильтры работают локально:

    ```bash
    dotnet test --filter "Category=unit"
    dotnet test --filter "Category=integration"
    ```

3.  Удалите (или переименуйте) прежние файлы workflow 31 и 32 — итоговый пайплайн будет единым. Создайте `.github/workflows/ci.yml` с содержимым из практического примера.

4.  Закоммитьте и запушьте:

    ```bash
    git add -A
    git commit -m "ci: итоговый пайплайн (кэш, матрица, сводка)"
    git push
    ```

5.  Во вкладке **Actions** изучите структуру запуска: job `build`, три параллельных запуска job `tests` (unit/integration/api), job `summary`. Обратите внимание на надпись «Cache restored» в шаге кэширования — при повторном пуше без изменений в `.csproj` кэш восстанавливается моментально.

6.  Специально сломайте один интеграционный тест и запушьте. Убедитесь, что:
    - падает только набор `integration` (благодаря `fail-fast: false`);
    - job `summary` всё равно выполняется и собирает отчёты;
    - в сводном артефакте есть три TRX-файла, включая упавший.

    Верните тест в рабочее состояние.

7.  Добавьте бейдж в `README.md` (замените `USER/REPO` на свой репозиторий) и убедитесь, что он отображается зелёным.

8.  Сделайте скриншоты: граф запуска (build → tests ×3 → summary), раздел Artifacts со сводным архивом, README с бейджем. Сохраните в `images`.

9.  Оформите `README.md` с разделом «CI» и зафиксируйте изменения.

### **Практический пример**

**Файл `.github/workflows/ci.yml`:**

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

env:
  DOTNET_VERSION: '10.0.x'
  CONFIGURATION: Release

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Клонирование репозитория
        uses: actions/checkout@v7

      - name: Установка .NET SDK
        uses: actions/setup-dotnet@v6
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Кэширование пакетов NuGet
        uses: actions/cache@v6
        with:
          path: ~/.nuget/packages
          key: nuget-${{ runner.os }}-${{ hashFiles('**/*.csproj') }}
          restore-keys: |
            nuget-${{ runner.os }}-

      - name: Восстановление зависимостей
        run: dotnet restore

      - name: Сборка
        run: dotnet build --no-restore --configuration ${{ env.CONFIGURATION }}

  tests:
    needs: build
    runs-on: ubuntu-latest

    strategy:
      fail-fast: false
      matrix:
        suite: [unit, integration, api]

    steps:
      - name: Клонирование репозитория
        uses: actions/checkout@v7

      - name: Установка .NET SDK
        uses: actions/setup-dotnet@v6
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Кэширование пакетов NuGet
        uses: actions/cache@v6
        with:
          path: ~/.nuget/packages
          key: nuget-${{ runner.os }}-${{ hashFiles('**/*.csproj') }}
          restore-keys: |
            nuget-${{ runner.os }}-

      - name: Восстановление зависимостей
        run: dotnet restore

      - name: Запуск набора «${{ matrix.suite }}»
        run: >
          dotnet test LibraryApp.Tests/LibraryApp.Tests.csproj
          --configuration ${{ env.CONFIGURATION }}
          --filter "Category=${{ matrix.suite }}"
          --logger "trx;LogFileName=${{ matrix.suite }}-results.trx"
          --results-directory TestResults

      - name: Публикация отчёта набора «${{ matrix.suite }}»
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: trx-${{ matrix.suite }}
          path: '**/TestResults/*.trx'

  summary:
    needs: tests
    if: always()
    runs-on: ubuntu-latest

    steps:
      - name: Скачивание всех отчётов
        uses: actions/download-artifact@v8
        with:
          pattern: trx-*
          merge-multiple: true
          path: TestResults

      - name: Сводка результатов
        run: |
          echo "Скачано TRX-файлов: $(ls TestResults/*.trx | wc -l)"
          ls -la TestResults
```

**Разметка тестов категориями:**

```csharp
// Обычные юнит-тесты
[Trait("Category", "unit")]
public class LibraryServiceTests { ... }

// Интеграционные тесты с SQLite (практика 27)
[Trait("Category", "integration")]
public class LibraryServiceSqliteTests { ... }

// API-тесты с реальным сервером (практика 28)
[Trait("Category", "api")]
public class LibraryApiTests { ... }
```

**Пояснения к ключевым местам:**

- `env` на уровне workflow хранит версию .NET и конфигурацию — они используются в нескольких местах; правка в одном месте меняет весь пайплайн;
- `needs: build` — тесты не начнутся, пока сборка не прошла: экономия ресурсов при компиляционных ошибках;
- `pattern: trx-*` + `merge-multiple: true` — скачивание всех артефактов с именами, начинающимися на `trx-`, в один каталог;
- `if: always()` на job `summary` — сводка строится даже при падении тестов;
- в `run: |` подставлять `${{ matrix.suite }}` можно, как и в любом другом поле.

**Бейдж в README:**


### **Варианты заданий**

**Вариант 1.** Полный пайплайн: кэш NuGet, матрица unit/integration/api, сводный артефакт, бейдж.

**Вариант 2.** То же; добавьте в `build` шаг публикации артефакта с бинарниками (`dotnet publish`) для скачивания.

**Вариант 3.** Матрица по конфигурациям `[Debug, Release]` для одного набора тестов; сравните время и объясните разницу.

**Вариант 4.** Матрица по трём наборам; в `summary` сформируйте текстовую сводку с количеством тестов из каждого TRX (например, через `grep -c`).

**Вариант 5.** Пайплайн с кэшем; продемонстрируйте в логах «Cache restored from key» при втором запуске. Приложите оба лога.

**Вариант 6.** Добавьте job `lint` (проверка форматирования через `dotnet format --verify-no-changes`), который идёт параллельно `build`.

**Вариант 7.** Пайплайн, который запускается ещё и по расписанию (`on: schedule: - cron: '0 3 * * 1'` — каждый понедельник в 3:00).

**Вариант 8.** В матрицу добавьте значение `ui` (headless Chrome, из практики 32) — четыре набора в одном пайплайне.

**Вариант 9.** Сводный job скачивает отчёты и дополнительно публикует один объединённый артефакт `all-reports`.

**Вариант 10.** Ограничьте пайплайн по времени (`timeout-minutes` на каждый job) и обоснуйте значения.

**Вариант 11.** Добавьте в `build` шаг `dotnet list package --vulnerable --include-transitive` — проверка пакетов на известные уязвимости; объясните вывод.

**Вариант 12.** Matrix включает `os: [ubuntu-latest, windows-latest]` для набора `unit`; сравните длительности и обсудите необходимость кросс-платформенных прогонов.

**Вариант 13.** Пайплайн с кэшем и матрицей; настройте `concurrency`, чтобы устаревшие запуски отменялись:

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

**Вариант 14.** Добавьте условный запуск job `integration` только для ветки `main` (`if: github.ref == 'refs/heads/main'`).

**Вариант 15.** Полный пайплайн + бейдж + раздел README «CI» со схемой пайплайна и скриншотами графа запуска.

### **Критерии оценки**

*   **5 (Отлично):**
    *   Единый workflow: build → tests (матрица 3 набора) → summary; всё выполняется.
    *   Кэш NuGet работает (подтверждено логом повторного запуска).
    *   Отчёты всех наборов собираются в сводный артефакт.
    *   Продемонстрировано: падение одного набора не скрывает остальные.
    *   Бейдж в README отображается; скриншоты в `images`; работа закоммичена.

*   **4 (Хорошо):**
    *   Пайплайн работает, но кэш не настроен или сводка не обязательна.
    *   Бейдж добавлен, но README не дополнен описанием CI.

*   **3 (Удовлетворительно):**
    *   Работает упрощённый вариант: тесты запускаются без матрицы, артефакты частично.
    *   Есть ошибки в синтаксисе `${{ }}` или фильтрах.

*   **2 (Неудовлетворительно):**
    *   Пайплайн не запускается; тесты не проходят; работа не сдана.

### **Подробное рассмотрение каждого пункта плана**

#### **1. Изоляция тестов: почему порядок выполнения не должен влиять на результат**

**Подробное объяснение:**

Каждый автоматический тест должен быть **изолированным** и **воспроизводимым**: не зависеть от других тестов и давать одинаковый результат при каждом запуске. xUnit запускает тесты **параллельно** (разные классы — одновременно), поэтому тесты, делящие общее состояние, превращаются в источник «плавающих» падений.

**Проблемы без управления жизненным циклом:**

*   **Зависимость между тестами:** состояние одного теста влияет на результат другого.
*   **Утечки ресурсов:** незакрытые соединения, файловые дескрипторы, «висящие» процессы браузеров.
*   **Накопление данных:** база данных или файлы переполняются данными предыдущих прогонов.
*   **Хрупкие тесты:** тест проходит «только вторым по счёту» или «только локально».

**Роль тестировщика** — создать для каждого теста **чистое, предсказуемое окружение**.

```csharp
// ПРОБЛЕМА: тесты зависят друг от друга
public class BadCounterTests
{
    private static int _sharedCounter = 0; // Статическое состояние — АНТИПАТТЕРН!

    [Fact]
    public void FirstTest_IncrementsCounter()
    {
        _sharedCounter++;
        Assert.Equal(1, _sharedCounter);
    }

    [Fact]
    public void SecondTest_IncrementsCounter()
    {
        _sharedCounter++;
        // Если этот тест выполнится первым — падение: значение будет 1, а не 2
        Assert.Equal(2, _sharedCounter);
    }
}
```

#### **2. Атрибуты тестов: `[Fact]` и `[Theory]`**

**Подробное объяснение:**

В xUnit тестовый метод помечается одним из двух атрибутов:

| Атрибут | Смысл | Когда использовать |
|---------|-------|--------------------|
| `[Fact]` | «Факт»: один метод — одно утверждение, данных нет | Проверка одного сценария без параметров |
| `[Theory]` | «Теория»: метод — правило, которое проверяется на **наборе данных** | Проверка логики на разных входных значениях |

`[Fact]` мы уже видели:

```csharp
[Fact]
public void GetUserName_ValidUser_ReturnsLogin()
{
    var user = new User { Login = "ivanov" };
    Assert.Equal("ivanov", user.Login);
}
```

Но если правило «сумма двух чисел» нужно проверить для десятка пар значений, писать десять почти одинаковых `[Fact]`-методов бессмысленно. Для этого существует `[Theory]` — вы можете назвать его **параметризованным тестом**. Классический пример без параметризации выглядит так (плохо):

```csharp
[Fact] public void Add_2and3_Returns5()  { Assert.Equal(5,  Calc.Add(2, 3)); }
[Fact] public void Add_0and0_Returns0()  { Assert.Equal(0,  Calc.Add(0, 0)); }
[Fact] public void Add_minus1and1()      { Assert.Equal(0,  Calc.Add(-1, 1)); }
```

Один и тот же код Assert повторяется, а при изменении сигнатуры метода придётся править все методы. `[Theory]` решает обе проблемы.

#### **3. Параметризация: `[InlineData]`, `[MemberData]`, `TheoryData` и `[ClassData]`**

**Подробное объяснение:**

**Способ 1: `[InlineData]` — данные «прямо в атрибуте».** Самый простой вариант для константных значений:

```csharp
public class CalculatorTests
{
    [Theory]
    [InlineData(2, 3, 5)]
    [InlineData(0, 0, 0)]
    [InlineData(-1, 1, 0)]
    [InlineData(int.MaxValue, 0, int.MaxValue)]
    public void Add_TwoNumbers_ReturnsSum(int a, int b, int expected)
    {
        var calculator = new Calculator();

        var result = calculator.Add(a, b);

        Assert.Equal(expected, result);
    }
}
```

Каждая строка `[InlineData]` превращается в **отдельный тестовый случай**: в выводе `dotnet test` и в панели Testing вы увидите четыре теста с одним именем и разными параметрами. Если упадёт только один набор — сразу видно, какой именно. Это главное преимущество параметризации: диагностика становится точнее.

**Ограничения `[InlineData]`:** значения должны быть **константами времени компиляции** — числа, строки, `bool`, `null`, элементы `enum`, `nameof(...)`. Нельзя передать `new DateTime(...)` или результат вызова метода.

Имя случая можно задать явно:

```csharp
[Theory]
[InlineData(0, 0, 0, DisplayName = "Ноль плюс ноль")]
[InlineData(2, 3, 5, DisplayName = "Положительные числа")]
public void Add_ReturnsSum(int a, int b, int expected) { /* ... */ }
```

**Способ 2: `[MemberData]` — данные из члена класса.** Когда значений много, они вычисляются в коде или содержат сложные объекты, данные выносятся в статическое свойство. Рекомендуемый типизированный контейнер — `TheoryData<T...>`:

```csharp
public class DiscountServiceTests
{
    public static TheoryData<decimal, string> InvalidDiscounts => new()
    {
        { -1m, "Скидка не может быть отрицательной" },
        { 0.5m, "Скидка не может быть меньше 1%" },
        { 101m, "Скидка не может превышать 100%" },
    };

    [Theory]
    [MemberData(nameof(InvalidDiscounts))]
    public void Apply_InvalidDiscount_ThrowsArgumentException(decimal discount, string expectedMessage)
    {
        var service = new DiscountService();

        var exception = Assert.Throws<ArgumentException>(() => service.Apply(discount));

        Assert.Contains(expectedMessage, exception.Message);
    }
}
```

Требования к `MemberData`:

*   свойство или поле должно быть `public static`;
*   возвращать `IEnumerable<object[]>` (или типизированный `TheoryData<...>`);
*   в атрибуте указывается `nameof` — переименование свойства не сломает тест молча.

Данные можно взять и из **другого класса**:

```csharp
[Theory]
[MemberData(nameof(TestData.InvalidLogins), MemberType = typeof(TestData))]
public void Register_InvalidLogin_Throws(string login) { /* ... */ }
```

**Способ 3: `[ClassData]` — данные из отдельного класса.** Класс реализует `IEnumerable<object[]>` и передаётся в атрибут целиком:

```csharp
public class ValidIsbnData : IEnumerable<object[]>
{
    public IEnumerator<object[]> GetEnumerator()
    {
        yield return new object[] { "978-5-496-01202-5" };
        yield return new object[] { "9785496012025" };
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}

[Theory]
[ClassData(typeof(ValidIsbnData))]
public void Validate_ValidIsbn_ReturnsTrue(string isbn)
{
    Assert.True(IsbnValidator.IsValid(isbn));
}
```

`[ClassData]` применяется реже — когда набор данных большой или переиспользуется в нескольких тестовых классах.

**Параметризация асинхронных тестов** работает так же: метод возвращает `Task`, а `[Theory]` дополняется `[InlineData]` или `[MemberData]`:

```csharp
[Theory]
[InlineData("978-5-496-01202-5")]
[InlineData("9785496012025")]
public async Task AddBookAsync_ValidIsbn_SavesBook(string isbn)
{
    var book = await _service.AddBookAsync("CLR via C#", "Джеффри Рихтер", isbn);

    Assert.Equal(isbn, book.Isbn);
}
```

#### **4. Конструктор и `IDisposable`: Setup и Teardown в xUnit**

**Подробное объяснение:**

В отличие от NUnit и MSTest, где используются атрибуты `[SetUp]`/`[TearDown]`, в xUnit применяется более явный подход:

*   **Конструктор класса** → выполняется **перед каждым** тестом (Setup);
*   **`IDisposable.Dispose()`** → выполняется **после каждого** теста (Teardown).

Важно понимать: xUnit создаёт **новый экземпляр тестового класса для каждого теста** — и для каждого набора данных `[Theory]` тоже. Поэтому конструктор — идеальное место для «свежего» состояния, а обычные поля класса не нужны `static` и не текут между тестами.

**Базовый шаблон:**

```csharp
public class DatabaseTests : IDisposable
{
    private readonly DatabaseConnection _db;
    private readonly string _testDatabaseName;

    // КОНСТРУКТОР = SETUP — выполняется ПЕРЕД КАЖДЫМ тестом
    public DatabaseTests()
    {
        _testDatabaseName = $"TestDB_{Guid.NewGuid()}"; // уникальное имя для изоляции
        _db = new DatabaseConnection();
        _db.CreateDatabase(_testDatabaseName);
        _db.Connect(_testDatabaseName);
    }

    // DISPOSE = TEARDOWN — выполняется ПОСЛЕ КАЖДОГО теста
    public void Dispose()
    {
        _db.DeleteDatabase(_testDatabaseName);
        _db.Dispose();
    }

    [Fact]
    public void AddUser_ReturnsSingleRow()
    {
        // Каждый тест получает СВОЮ копию базы данных
        _db.Execute("INSERT INTO Users (Name) VALUES ('Test User 1')");

        var count = _db.ExecuteScalar<int>("SELECT COUNT(*) FROM Users");

        Assert.Equal(1, count);
    }

    [Fact]
    public void AddAnotherUser_ReturnsSingleRow()
    {
        // Этот тест НЕ видит данные из предыдущего
        _db.Execute("INSERT INTO Users (Name) VALUES ('Test User 2')");

        var count = _db.ExecuteScalar<int>("SELECT COUNT(*) FROM Users");

        Assert.Equal(1, count); // Всегда 1, а не 2!
    }
}
```

**Преимущества подхода xUnit:**

*   **Явность:** видно, что является настройкой, а что — очисткой.
*   **Изоляция:** новый экземпляр класса на каждый тест исключает «протекание» состояния.
*   **Гарантия очистки:** xUnit вызывает `Dispose()` даже при падении теста с исключением.

**Пример для тестировщика Web UI:** очистка дорогого ресурса (браузера) через `Dispose()`:

```csharp
public class WebUiTests : IDisposable
{
    private readonly IWebDriver _driver;

    public WebUiTests()
    {
        // Setup: для каждого теста — свой чистый экземпляр браузера
        _driver = new ChromeDriver();
        _driver.Manage().Window.Maximize();
    }

    public void Dispose()
    {
        // Teardown: браузер закроется даже если тест упал
        _driver.Quit();
        _driver.Dispose();
    }

    [Fact]
    public void Login_ValidCredentials_RedirectsToDashboard()
    {
        _driver.Navigate().GoToUrl("https://example.com/login");
        _driver.FindElement(By.Id("username")).SendKeys("testuser");
        _driver.FindElement(By.Id("password")).SendKeys("password");
        _driver.FindElement(By.Id("login-btn")).Click();

        Assert.Equal("https://example.com/dashboard", _driver.Url);
    }
}
```

> **Скриншот при падении.** В xUnit, в отличие от NUnit, из `Dispose()` нельзя напрямую узнать результат теста (нет `TestContext.Result`). Поэтому снимок экрана делают в блоке `catch` самого теста: перехватить исключение, сохранить скриншот и **пробросить исключение дальше** (`throw;`). Либо используют события тестового раннера. Подробнее приём разбирается в Разделе 6.

#### **5. Фикстуры уровня класса: `IClassFixture<T>`**

**Подробное объяснение:**

Некоторые ресурсы слишком **дорогие**, чтобы создавать их для каждого теста: запуск браузера, подготовка базы данных, поднятие тестового сервера. Если ресурс можно переиспользовать между тестами **одного класса**, применяется механизм фикстур.

**`IClassFixture<T>`** создаёт ресурс **один раз на тестовый класс** и передаёт его в конструктор каждого теста.

```csharp
// 1. Создаём класс фикстуры
public class DatabaseFixture : IDisposable
{
    public DatabaseConnection Db { get; private set; }
    public string DatabaseName { get; private set; }

    public DatabaseFixture()
    {
        DatabaseName = $"SharedTestDB_{Guid.NewGuid()}";
        Db = new DatabaseConnection();
        Db.CreateDatabase(DatabaseName);
        Db.Connect(DatabaseName);

        Db.RunMigrations(); // дорогая операция — выполняем один раз на класс
    }

    public void Dispose()
    {
        Db.DeleteDatabase(DatabaseName);
        Db.Dispose();
    }
}

// 2. Подключаем фикстуру к тестовому классу
public class UserRepositoryTests : IClassFixture<DatabaseFixture>
{
    private readonly DatabaseFixture _fixture;
    private readonly UserRepository _repository;

    // Фикстура передаётся через конструктор автоматически
    public UserRepositoryTests(DatabaseFixture fixture)
    {
        _fixture = fixture;
        _repository = new UserRepository(_fixture.Db);

        // Очищаем таблицу перед каждым тестом — данные не «протекают»
        _fixture.Db.Execute("DELETE FROM Users");
    }

    [Fact]
    public void CreateUser_ValidData_UserIsCreated()
    {
        var user = new User { Name = "John", Email = "john@test.com" };

        var result = _repository.CreateUser(user);

        Assert.True(result > 0);
        Assert.Equal("John", _repository.GetUser(result).Name);
    }

    [Fact]
    public void GetUser_NonExistingUser_ReturnsNull()
    {
        Assert.Null(_repository.GetUser(999));
    }
}
```

**Когда использовать `IClassFixture<T>`:**

*   инициализация тестового сервера или API;
*   подготовка базы данных со схемой/миграциями;
*   создание дорогих внешних сервисов, кэшей, конфигураций.

**Важный нюанс:** фикстура живёт весь класс, поэтому данные внутри неё **изменяемы** — состояние нужно очищать в конструкторе теста (как `DELETE FROM Users` в примере), иначе тесты начнут влиять друг на друга.

#### **6. Фикстуры уровня коллекции: `ICollectionFixture<T>`**

**Подробное объяснение:**

Когда ресурс должен разделяться между **несколькими тестовыми классами**, используется `ICollectionFixture<T>`. Тестовые классы, входящие в одну коллекцию, **не выполняются параллельно друг с другом** — это дополнительно защищает общий ресурс от гонок.

```csharp
// 1. Фикстура: общий HTTP-клиент к тестовому стенду
public class TestApiFixture : IDisposable
{
    public HttpClient Client { get; }
    public string BaseUrl { get; }

    public TestApiFixture()
    {
        BaseUrl = "http://localhost:5080";
        Client = new HttpClient { BaseAddress = new Uri(BaseUrl) };
        // Здесь можно дождаться готовности стенда или прогреть соединение
    }

    public void Dispose()
    {
        Client.Dispose();
    }
}

// 2. Определяем коллекцию (класс-маркер без кода)
[CollectionDefinition("ApiCollection")]
public class ApiCollection : ICollectionFixture<TestApiFixture>
{
}

// 3. Классы попадают в одну коллекцию по имени
[Collection("ApiCollection")]
public class BooksApiTests
{
    private readonly TestApiFixture _fixture;

    public BooksApiTests(TestApiFixture fixture)
    {
        _fixture = fixture;
    }

    [Fact]
    public async Task GetBooks_ReturnsBookList()
    {
        var response = await _fixture.Client.GetAsync("/api/books");

        response.EnsureSuccessStatusCode();
        var content = await response.Content.ReadAsStringAsync();
        Assert.Contains("books", content);
    }
}

[Collection("ApiCollection")] // Тот же стенд и клиент!
public class AuthorsApiTests
{
    private readonly TestApiFixture _fixture;

    public AuthorsApiTests(TestApiFixture fixture)
    {
        _fixture = fixture;
    }

    [Fact]
    public async Task GetAuthors_ReturnsAuthorList()
    {
        var response = await _fixture.Client.GetAsync("/api/authors");

        response.EnsureSuccessStatusCode();
    }
}
```

**Иерархия фикстур по «стоимости» ресурса:**

| Ресурс нужен… | Механизм |
|---------------|----------|
| Одному тесту | Создать в тесте или в конструкторе |
| Всем тестам одного класса | `IClassFixture<T>` |
| Нескольким классам | `ICollectionFixture<T>` |

> Для тестирования ASP.NET Core API на реальном приложении (без запуска внешнего стенда) применяется `WebApplicationFactory<T>` из пакета `Microsoft.AspNetCore.Mvc.Testing` — он подробно разбирается в Разделе 8 (интеграционные тесты).

#### **7. Лучшие практики и распространённые ошибки**

**Лучшие практики:**

1.  **В конструкторе — только инициализация:**

    ```csharp
    // ХОРОШО
    public class GoodTestClass : IDisposable
    {
        private readonly DatabaseConnection _db;

        public GoodTestClass()
        {
            _db = new DatabaseConnection(); // только подготовка ресурса
        }

        public void Dispose()
        {
            _db.Dispose(); // только очистка
        }
    }

    // ПЛОХО: бизнес-логика в конструкторе
    public class BadTestClass
    {
        public BadTestClass()
        {
            // Тестовые сценарии не должны быть в конструкторе!
            new UserService().CreateUser("test"); // АНТИПАТТЕРН
        }
    }
    ```

2.  **Очистка не должна «ронять» тест.** Исключение в `Dispose()` перезапишет результат теста:

    ```csharp
    public void Dispose()
    {
        try
        {
            _resource?.Dispose();
            if (File.Exists(_tempFile))
                File.Delete(_tempFile);
        }
        catch (Exception ex)
        {
            // Логируем, но не падаем: teardown не должен влиять на результат
            Console.WriteLine($"Cleanup warning: {ex.Message}");
        }
    }
    ```

3.  **Уникальные данные вместо очистки там, где это проще:**

    ```csharp
    public class IsolatedTests
    {
        private readonly string _testId = Guid.NewGuid().ToString("N");

        [Fact]
        public void CreateUser_UsesUniqueData()
        {
            var login = $"test_user_{_testId}"; // гарантированно уникален
            // ...
        }
    }
    ```

4.  **Ставьте `IDisposable`, если владеете ресурсом** (браузер, соединение, файл, сервер) — иначе на CI будут утечки и «зависшие» процессы.

**Распространённые ошибки:**

1.  **Статическое состояние:**

    ```csharp
    // АНТИПАТТЕРН: тесты влияют друг на друга и на параллельные тесты
    public class StaticStateTests
    {
        private static int _counter = 0;
    }
    ```

2.  **Тесты, оставляющие данные после себя:**

    ```csharp
    // ПЛОХО: пользователь остаётся в БД, повторный запуск упадёт с "already exists"
    [Fact]
    public void CreateUser_LeavesDataInDatabase()
    {
        new UserService().CreateUser("test_user");
    }

    // ХОРОШО: данные уникальны или очищаются
    [Fact]
    public void CreateUser_WithUniqueLogin_Succeeds()
    {
        var login = $"test_user_{Guid.NewGuid()}";
        var service = new UserService();

        try
        {
            service.CreateUser(login);
            Assert.True(service.UserExists(login));
        }
        finally
        {
            service.DeleteUser(login);
        }
    }
    ```

3.  **Попытка передать в `[InlineData]` не-константу:**

    ```csharp
    // НЕ СКОМПИЛИРУЕТСЯ: значение должно быть константой
    [InlineData(DateTime.Now, "2026-01-01")]
    // Нужны вычисляемые данные — используйте [MemberData]
    ```

4.  **Общий изменяемый ресурс без очистки:** `IClassFixture`-база «накапливает» записи, и тесты начинают падать «через один». Помните: фикстура — общая, изоляцию данных обеспечивает конструктор теста.

### **Резюме**

1.  Тесты должны быть **изолированными**: xUnit запускает классы параллельно, поэтому общее состояние — источник «плавающих» падений.
2.  `[Fact]` — одиночный тест; `[Theory]` — параметризованный, превращающий набор данных в отдельные тестовые случаи.
3.  Данные для `[Theory]` задаются через `[InlineData]` (константы), `[MemberData]` (статический член, рекомендуется `TheoryData<T>`), `[ClassData]` (отдельный класс).
4.  **Setup и Teardown** в xUnit — это **конструктор** и **`IDisposable.Dispose()`**; новый экземпляр класса создаётся на каждый тест (и на каждый набор `[Theory]`).
5.  **`IClassFixture<T>`** — общий ресурс для всех тестов класса; состояние внутри фикстуры нужно очищать в конструкторе.
6.  **`ICollectionFixture<T>`** — общий ресурс для нескольких классов; тесты коллекции не выполняются параллельно друг с другом.
7.  Выбирайте минимально возможную область жизни ресурса: тест → класс → коллекция; очистка в `Dispose()` не должна выбрасывать исключения.

### **Контрольные вопросы**

1.  Чем отличаются атрибуты `[Fact]` и `[Theory]`? В каких случаях применяется каждый?
2.  Сколько раз выполнится конструктор тестового класса с одним тестом `[Theory]` и пятью строками `[InlineData]`? Почему?
3.  Какие значения можно передать через `[InlineData]`, а какие — нельзя? Что использовать для вычисляемых данных?
4.  Какие требования предъявляются к члену класса, на который ссылается `[MemberData]`? Зачем нужен `TheoryData<T>`?
5.  Чем подход xUnit к Setup/TearDown отличается от NUnit/MSTest? Какие два механизма его заменяют?
6.  Когда следует использовать `IClassFixture<T>` вместо конструктора, а когда — `ICollectionFixture<T>`?
7.  Почему статические поля в тестовых классах считаются антипаттерном? Как связан с этим параллельный запуск тестов?
8.  **Практическая задача:** напишите параметризованный тест для метода `IsValid(string isbn)` с тремя наборами валидных значений через `[InlineData]` и одним набором ошибочных данных через `[MemberData]` с `TheoryData<string, string>` (значение — ожидаемое сообщение об ошибке).
